## Introduction

> **New to the design?** Start with [the main article](/blog/digital-branch-concierge) for the business case and architecture. This page is the hands-on LangGraph build: setup, tests and recorded results.

LangGraph is the second build in this series, and the engineer's version of the concierge. The outer process is a typed state graph, the agent is a LangChain agent inside it, and the routing and authorisation rules are code you can read and unit test without a model. LangSmith sits alongside for tracing, evaluation, prompt versions and human review. The bank branch is the worked example, and the question is the same as for n8n: how can an agent do useful work while the organisation retains control?

The comparison is controlled rather than identical. The same four demo customers, knowledge documents, skills, risk ratings, gate rules and twelve test conversations are used, and the model is the same deepseek-flash. The differences are noted where they matter: human decisions are resumed in Studio rather than Slack, the evaluation also scores which skill ran, and two test expectations were corrected after review. This walkthrough follows those conversations through the graph, the pauses for a person and the evidence behind a scored assessment of the controls. The code, tests and scripts are in the repository so you can run the same conversations yourself.

## What you'll build

<TickList>

<TickItem>

**A concierge agent** built with LangChain's `create_agent` that meets the customer, works out what they actually need and either answers, does the small job itself or hands over with context.

</TickItem>

<TickItem>

**Four skills as typed tools**, each with a Pydantic input schema, a risk rating in one registry and its own ownership check: print statement, fetch balance, book appointment and update contact details. Three read-only tools handle opening hours, appointment slots and the knowledge search.

</TickItem>

<TickItem>

**Two deterministic gates.** Pre-action authorisation as agent middleware, checking every proposed call before it runs, and an impact and policy gate after the agent, a pure function over structured facts that decides whether the outcome needs a person. The agent never makes either call.

</TickItem>

<TickItem>

**Two human decision points** resumed in LangSmith Studio: an approval before a contact-detail change runs, and a review before a flagged reply reaches the customer. The reply review records the named approver in a decision table.

</TickItem>

<TickItem>

**Guardrails in and out, and a LangSmith loop around them.** Traces are masked before they leave the machine, a dataset and code evaluators score each change, prompts move through Staging and Production, and held or refused conversations land in a review queue.

</TickItem>

</TickList>

## The shape in code

The article's diagram maps onto one graph, one agent and a learning loop in LangSmith.

<ScrollCards label="The five parts of the LangGraph concierge architecture" hint="Scroll through the five parts">

<ScrollCard number="01" title="Outer process">

A `StateGraph` with eight nodes: identify, guard_in, agent, guard_out, assemble_facts, human_decision, record_decision and release. The routing and authorisation rules are deterministic Python. The input guardrail combines deterministic patterns with a model classifier. The graph owns identification, routing and the decision record. The agent sits inside that process, not above it.

</ScrollCard>

<ScrollCard number="02" title="The agent">

A `create_agent` subgraph combines the system prompt, pulled from LangSmith Prompts by its Production environment, the chat model and the seven tools. Middleware wraps it: authorisation, the approval pause, model and tool call limits of 8 and model retries.

</ScrollCard>

<ScrollCard number="03" title="Skills">

Four `@tool` functions with typed inputs, each checking ownership against the identified customer before doing the work, and each returning a typed result with its risk rating and status. The agent can call them but cannot change them, and a refusal comes back as a tool message it reads and responds to.

</ScrollCard>

<ScrollCard number="04" title="Pre-action approval">

LangChain's `HumanInTheLoopMiddleware` pauses before `update_contact_details`. Its condition only asks for approval when the call is authorised and its arguments are valid, so a person is never asked to approve a call the gate would refuse. The graph saves its state and waits for a resume value.

</ScrollCard>

<ScrollCard number="05" title="Read-only tools and knowledge">

opening_hours, find_slots and knowledge only read. The knowledge tool scores keywords over the same two documents the n8n build used. The article's design puts read-only lookups behind MCP and knowledge behind retrieval; these local tools keep the demo portable and the comparison even.

</ScrollCard>

</ScrollCards>

One detail is worth noticing before you build. The run context names the customer when a conversation starts, and `identify` copies that into the graph's saved state on the first turn. From then on the gate, the approval check, the skills and the decision record all read the customer from state. A resumed pause cannot switch the customer, even when the resume arrives without a context, as it does from Studio. Testing caught that gap in my first version, and the build now closes it.

Two vocabulary points help when moving between the article and LangChain.

**Skills.** LangChain's Deep Agents also use "skills", for instruction files an agent loads on demand to guide how it approaches a task. Here, skills are bounded tools that control what the agent can do. The two are complementary: instruction skills guide behaviour; tool skills limit reach.

**Middleware.** In LangChain 1.x, middleware is code that runs before or after the model, or around each tool call, inside the agent loop. This build puts both the authorisation check and the approval pause there, so they apply to every call the agent proposes.

## Before you start

- **Python 3.12 and uv.** uv installs the pinned dependencies from the lock file. The build was run with LangChain 1.4, LangGraph 1.2 and langsmith 0.12.
- **A DeepSeek API key** for deepseek-flash, with thinking turned off for parity with the n8n build and lower token costs.
- **A LangSmith account.** The Developer plan is sufficient: it includes one free seat and a monthly trace allowance, with usage beyond that billed. EU accounts use the EU endpoint.
- **Chrome, Edge or Firefox** for LangSmith Studio. Safari blocks the hosted Studio page from reaching the local server.
- **[The repository](https://github.com/GoldenPassport/digital-branch-concierge)**, which holds the code, tests, scripts, the four demo customers, the knowledge documents and the twelve test conversations. It is linked in Setup files below.

Use the supplied demo records, not real customer data. The skills simulate their actions: update_contact_details and book_appointment return a confirmation but do not change a record or store a booking. The build tests authorisation, pauses and routing on those results, not persistence, reversal or integration with banking systems. This is a learning build, not a production banking service or a certification of regulatory compliance. Model responses may vary, so compare each run with the expected route rather than expecting identical wording.

## Build it

The walkthrough has four parts: **Setup** prepares the project and LangSmith, **Review** reads the gates in code, **Run it** exercises the test conversations and **Observations** shows where to find the evidence behind the scorecard.

### Review

<ProcessSteps start={5}>

<ProcessStep title="Read a skill before you run it" outcome="you can point at the two places that stop a risky action before it happens.">

- Open `skills/fetch_balance.py`. The function takes a typed `account_id`, asks `authorise` whether the bound customer owns that account and returns a refusal result before doing any work if not. <Shot src="/posts/digital-branch-concierge/langgraph-steps/review-skill-code.webp" alt="The fetch_balance skill: it calls authorise with the bound customer and the account id, returns a refusal if not authorised, and only then reads the balance." caption="The ownership check comes first" />
- Open `agent.py` and find `AuthoriseToolCalls`. It runs the same check around every proposed tool call, sync and async, and turns a refusal into a tool message carrying the risk rating. Anything not in `registry.py` is refused.
- Find the `HumanInTheLoopMiddleware` block. Only `update_contact_details` pauses, and only when the call is authorised and its arguments validate.

</ProcessStep>

<ProcessStep title="Follow the outer process" outcome="you can trace where accountability, containment and lineage each sit in the graph.">

- `identify` binds the customer, session and test id to the conversation. In Studio, set them in the run context; the default customer is C1003, Chloe Martin. <Shot src="/posts/digital-branch-concierge/langgraph-steps/review-graph-identify.webp" alt="The top of the concierge graph in LangSmith Studio: start, identify, guard_in, then the agent." caption="identify and guard_in open the graph" />
- `guard_in` runs deterministic jailbreak patterns first, then a model classifier for jailbreak and off-topic scores at 0.7. A failure skips the agent entirely.
- `guard_out` masks card numbers, IBANs, sort codes with account numbers and secret keys in the reply.
- `assemble_facts` builds what the gate reads, with no model in it: the highest risk of any tool called, taken from the registry, the customer's open complaint and vulnerability flags, policy keywords in the request or earlier in the conversation, a tool result it cannot read, and a reply that is empty or claims an outcome such as an account closed.

</ProcessStep>

<ProcessStep title="Check the gate fails safe" outcome="only an explicit, positive classification reaches the customer directly.">

- Open `gates/impact_policy.py`. The gate is four lines: refused if the input guardrail failed, straight through only if there are no reasons, otherwise review. <Shot src="/posts/digital-branch-concierge/langgraph-steps/review-gate-code.webp" alt="The impact and policy gate: refused if the input guardrail failed, straight_through only when there are no reasons, otherwise review." caption="The whole gate" />
- Any reason at all, including no identified customer or an empty reply, goes to a person. There is no rule to forget, because straight through is the exception.
- Open `human/decision.py`. A resume value without a recognised decision or a named approver is held, not released.

</ProcessStep>

</ProcessSteps>

- Open the tracing project. Every conversation turn is one trace, with the route and outcome in its output. <Shot src="/posts/digital-branch-concierge/langgraph-steps/05-langsmith-project.webp" alt="The concierge-demo tracing project listing the evidence runs with input, output, start time, latency, tokens and cost." caption="The evidence runs in the tracing project" />

- Click an `identify` run and open Attributes. The metadata carries the test id, session and a pseudonymous customer reference, so runs can be filtered without the customer's details. <Shot src="/posts/digital-branch-concierge/langgraph-steps/obs-explainability-trace-metadata.webp" alt="The identify run's Attributes tab with metadata including customer_ref as a hashed pseudonym, session_id server-T10, test_id T10 and thread_id." caption="Trace metadata" />

It does not catch other sensitive details a customer types in free text, and the local checkpoints, the SQLite decision record and the calls to DeepSeek are separate data flows with their own controls. <Shot src="/posts/digital-branch-concierge/langgraph-steps/obs-explainability-masked.webp" alt="The T10 trace with the customer's reply shown as [email] please." caption="Masked before it left the machine" />

### Potential findings

These are early observations from a limited number of runs on the local development server and a LangSmith Developer plan. I may have missed a setting or misread a result, so treat them as things to check in your own setup rather than settled conclusions.

<ScrollCards label="Six potential findings from initial testing" hint="Scroll through the six findings">

<ScrollCard number="01" title="Custom middleware needs an async hook">

My authorisation middleware first had only the sync `wrap_tool_call`. The offline tests passed, but the first tool call on the dev server failed, because the server runs graphs asynchronously. Adding `awrap_tool_call` fixed it, and a test now covers the async path.

</ScrollCard>

<ScrollCard number="02" title="A resume carries no run context">

Most likely my design. The decision record and the skills read the customer from the run context, and a resume from Studio arrived without one, so two decisions were recorded against the default customer. It happened to be the right customer in that run. Binding the customer to the conversation in state on the first turn fixed it for every node, middleware and skill.

</ScrollCard>

<ScrollCard number="03" title="Feedback written from inside the server did not appear">

Recording route and outcome as LangSmith feedback from inside a node returned an id on the dev server, but the feedback was not stored in my runs, while the same call from a local script worked. Putting route and outcome in the graph's output worked cleanly, and automation rules can filter on it.

</ScrollCard>

<ScrollCard number="04" title="Paused threads did not survive a restart">

When the local dev server stopped, the threads were still listed but their paused state was empty. The dev server is designed for local iteration, so this is expected behaviour rather than a fault, but it matters for a demo: finish a paused conversation before restarting, and use a persistent deployment for anything that must wait.

</ScrollCard>

<ScrollCard number="05" title="Extended retention is ticked by default">

When a rule adds traces to an annotation queue, Extend Data Retention is ticked by default. That keeps those traces on extended retention, which is billed separately. It is easy to miss, so untick it unless you need it.

</ScrollCard>

<ScrollCard number="06" title="A code review found gaps the tests did not cover">

After the recorded runs, a review of the code found boundaries that held for one turn but not the whole conversation. A follow-up such as "Yes, please do that" after a closure request could go straight through. An edited reply skipped output masking, callers received the unmasked message history and a malformed tool result could lower the risk. All of it is now fixed and covered by tests, and the repository README lists each change. The evidence on this page comes from the runs before those fixes; the twelve routes are unchanged.

</ScrollCard>

</ScrollCards>

These observations show why a repeatable test set matters alongside a convincing demonstration.

### Keeping policy consistent as agents multiply

The gate's rules sit in this project's Python, and each skill carries its own authorisation check alongside the middleware. That is manageable for one concierge, and code review gives every rule change a history. If teams copy the pattern across many agents, policy can still diverge: a rule change must reach every copy, and a new tool could be added without a registry entry.

The next step is shared policy: the registry, risk ratings and gate rules as a versioned package or policy service used by every agent, with changes reviewed by policy owners and tested against a shared evaluation set. LangSmith's Staging and Production environments already show how that can work for prompts. Shared rules improve consistency; representative tests must still show that those rules recognise the requests they are meant to catch.

## Opportunities for the next build

Two enhancements from the article's design were left out to keep the comparison even with n8n, and both are natural next steps.

- **Retrieval over embeddings.** The knowledge tool scores keywords over two short documents, which is enough for twelve test conversations. A real knowledge base would use a vector store with a sync job that re-indexes a document when its source changes and removes chunks that are out of date.
- **Evaluation in the delivery pipeline.** The learning loop ran by hand in this build: a review, a staged change, an experiment and a decision. Running the experiment on every pull request, blocking a promotion when a score drops and scoring reply quality alongside routes would make the loop continuous. The agent still never changes itself, and the gate rules and the ADM line stay outside the loop.

## Conclusion

Can a code-first framework give an agent room to act while keeping consequential decisions with people? This build offers a promising answer. The routine requests went straight through, the higher-impact requests paused for a person and the traces showed which tools ran and why the gate chose its route, with the configured identifiers masked before they left the machine.

What stayed with me was the loop. A proposed change could be staged, evaluated, reviewed and rolled back without touching Production, and a human review corrected a test rather than the agent. That is governance of change, not just of individual runs, and it is where LangSmith adds the most to LangGraph.

My score of **8 out of 10** reflects that foundation, not a claim of production readiness. The opportunities above set out what would take it further.

This build left me confident that LangGraph and LangSmith can carry governed agentic automation in code. They give engineers precise control and give the organisation evidence for every run and every change. For me, that is the value: useful freedom for the agent, tested control at the edges and a reviewed path for everything that improves. That is what Enterprise Agency looks like in code.
