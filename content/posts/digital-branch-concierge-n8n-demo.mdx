## Introduction

> **Reading the Article tab first?** Switch back if you have not yet. This page assumes you know what the branch concierge is, why the shape is a sandwich rather than a dial and where the automated decision-making line sits. What follows is the hands-on n8n build.

n8n is the fastest of the three routes to a working concierge, which is why it goes first. Nothing here needs code beyond a few expressions, and the whole sandwich (outer process, agent and skills) is built from nodes you drag onto a canvas in an afternoon.

Building it is the easy half. The rest of this page is the evidence: twelve test conversations, the runs they produced, what the gate did with each one and a scored verdict on whether the controls held. Every screenshot comes from that instance, and the workflow files are in the repository, so you can run the same tests yourself.

## What you'll build

<TickList>

<TickItem>

**A concierge agent** on n8n's AI Agent node that meets the customer, works out what they actually need and either answers, does the small job itself or hands over with context.

</TickItem>

<TickItem>

**Four skills as sub-workflows**, each with a typed input, a typed output and a risk rating: print statement, fetch balance, book appointment and update contact details.

</TickItem>

<TickItem>

**Two deterministic gates.** Pre-action authorisation at the top of every skill, so a risky call is stopped before it runs, and an impact and policy gate after the agent, a plain Switch node that decides whether the outcome needs a person. The agent never makes either call.

</TickItem>

<TickItem>

**A human approval step** using Slack's send-and-wait, so a named decision owner can change the outcome before the customer sees it.

</TickItem>

<TickItem>

**Guardrails in and out**, a scoped memory and three read-only Code Tools, one of which searches the knowledge documents by keyword. Every run is logged step by step, and an Evaluations hook scores the whole test set on demand.

</TickItem>

</TickList>

## Before you start

- **n8n 2.x**, cloud or self-hosted. The Guardrails node, Data Tables and Evaluations all need a recent release. The workflows were built and run on n8n cloud 2.39.
- **A DeepSeek credential** for the two chat models, which run deepseek-flash, DeepSeek's current V4.1-Flash model. All three demos in this series use DeepSeek where they can, to keep the token cost low and the comparison fair.
- **A Slack workspace** you can add a bot to, for the two approval steps, with a channel called #concierge-approvals. Any other send-and-wait node works if you would rather not use Slack.
- **[The repository](https://github.com/GoldenPassport/digital-branch-concierge)**, which holds the five workflow files, the four demo customers, the knowledge documents and the twelve test conversations. It is linked in Setup files below.

## The shape on the canvas

The article's diagram maps onto five workflows.

<ScrollCards label="The five parts of the n8n concierge architecture" hint="Scroll through the five parts">

<ScrollCard number="01" title="Outer process">

The main workflow has 31 nodes: Chat Trigger, Identify customer, Guardrails in, the AI Agent, Guardrails out, Assemble facts, the Impact and policy gate, Human decision (Slack) and the replies, plus When running evaluation and Record metrics for the test set. This is where accountability lives, and none of it is a model.

</ScrollCard>

<ScrollCard number="02" title="The agent">

One AI Agent node combines a system prompt that defines the concierge role and what it must never decide, a chat model, Simple Memory keyed by the identified customer and the session and the tools it may call.

</ScrollCard>

<ScrollCard number="03" title="Skills">

Four sub-workflows each start with a trigger that declares a typed input, followed by a pre-action authorisation check, the work and a typed result carrying the skill's risk rating back to the process. The agent reaches them through Call n8n Workflow Tool nodes. It cannot see inside them or change them.

</ScrollCard>

<ScrollCard number="04" title="Pre-action approval">

Pre-action approval (Slack), n8n's human review step, sits between the agent and the update contact details skill. The agent proposes the call and its parameters, a decision owner approves or declines it in Slack, and only an approved call reaches the skill.

</ScrollCard>

<ScrollCard number="05" title="Read-only tools and knowledge">

Three Code Tools only read: opening_hours, find_slots and knowledge, which searches the fees and policy documents by keyword. The article's design puts read-only lookups behind MCP. The Code Tools keep the demo portable and can be swapped for an MCP Client Tool in one step.

</ScrollCard>

</ScrollCards>

One detail is worth noticing before you build. Every skill takes a session_customer_id input, and the tool node fills it with an expression over the Identify customer node, not with a value from the model. The skill then checks that the requested account belongs to that customer. The process supplies the fact the model cannot be allowed to invent.

A note on n8n's own vocabulary, because it is close to the article's but not identical. n8n's building blocks for agents are the AI Agent node, memory, tools, human-in-the-loop approvals, guardrails, observability, evaluations and MCP. Its own advice is to mix deterministic automation steps with AI to increase reliability, which is the sandwich in one sentence. Two words differ. n8n's "skills" template uses the Agent Skills convention, instruction files pulled from a repository into the system prompt that tell the model how to approach a kind of task. The concierge's skills are sub-workflows, bounded capabilities that limit what the model can do. The two are complementary: instruction skills shape behaviour, sub-workflow skills bound reach. And the approval before a tool runs is n8n's own human review step, added from the Tools panel of the agent node (n8n 2.6 and later): it sits on the connection between the agent and a tool, so the decision owner sees the proposed call before the skill is invoked. The demo uses it in front of the one skill that writes.

## Build it

Four groups of steps. Setup gets the instance ready and ends with a check that everything is where it should be. Review examines a skill, the outer process and the fail-safe gate before anything is tested. Run it sends the test conversations manually and as an evaluation. Observations are the steps that lead to the evidence for each row of the scorecard.

### Setup

<ProcessSteps>

<ProcessStep title="Sign in to n8n cloud" outcome="you are on the Overview page of your instance, with the Workflows tab selected.">

The build runs on n8n cloud, so the first step is the sign-in page. Nothing here is specific to the concierge.

- Go to app.n8n.cloud/login. <Shot src="/posts/digital-branch-concierge/n8n-steps/01-cloud-login-full.png" alt="The n8n cloud sign-in page: a heading reading Go to your n8n instance, a field for the n8n account name followed by .app.n8n.cloud and a Go to instance button." caption="The n8n cloud sign-in page" />
- Type your instance name, the part before .app.n8n.cloud. <Shot src="/posts/digital-branch-concierge/n8n-steps/01-cloud-login-a.png" alt="The sign-in page with the account name field highlighted and a label reading 1. Type your instance name." caption="Type your instance name" />
- Click Go to instance, then sign in with your n8n credentials when your instance asks. <Shot src="/posts/digital-branch-concierge/n8n-steps/01-cloud-login-b.png" alt="The sign-in page with the Go to instance button highlighted and a label reading 2. Click here." caption="Click Go to instance" />
- No instance yet? The free trial link on the same page creates one, and the demo fits inside the trial limits.

</ProcessStep>

<ProcessStep title="Import the five workflows" outcome="five Concierge workflows in your list, all published, with the four tool nodes in the main process pointing at the four skills.">

Each workflow file is imported into its own new workflow. Import the four skills first, so the main process can point at them, then import the main process.

- Click Create workflow, then open the three-dot menu next to the workflow name and choose Import, then From file. <Shot src="/posts/digital-branch-concierge/n8n-steps/02-import-menu.png" alt="The workflow menu open, with Import highlighted and the From file option beside it." caption="The Import menu" />
- Pick the file, starting with 01-skill-print-statement.json. The nodes appear on the canvas.
- Click the workflow name at the top, replace it with the name in the file (Concierge skill: Print statement), press Return, then click the canvas and save.
- Repeat for the other three skills, then 05-concierge-main.json.
- In the main process, open each of the four Call n8n Workflow Tool nodes (print_statement, fetch_balance, book_appointment, update_contact_details) and select the matching skill from the Workflow list, since the cloud assigns new ids on import. <Shot src="/posts/digital-branch-concierge/n8n-steps/02-tool-nodes.png" alt="The main process canvas zoomed in on the AI Agent, with print_statement, fetch_balance and book_appointment highlighted as three skill tools and update_contact_details highlighted behind the pre-action approval." caption="The four skill tool nodes" /> <Shot src="/posts/digital-branch-concierge/n8n-steps/02-tool-workflow-select.png" alt="The print_statement tool node open, with the Workflow field highlighted and the instance-specific workflow id blurred." caption="The Workflow field on a tool node" />
- Publish each of the four skills with the Publish button at the top right. A workflow called by another workflow must be published, or the tool call fails with "Workflow is not active and cannot be executed". The first live run of this demo hit that error, and the agent's reply, an apology and an offer to try again or point to the counter, is worth keeping as evidence that a failed skill degrades gracefully. <Shot src="/posts/digital-branch-concierge/n8n-steps/02-skill-published.png" alt="The Concierge skill: Print statement workflow with the Published control at the top right highlighted." caption="A published skill" />
- Publish the main process as well. The Approve and Decline buttons in Slack call back to a webhook that only answers for a published workflow. The first approval attempt on this build returned a 404 to Slack for that reason.

</ProcessStep>

<ProcessStep title="Add the DeepSeek credential" outcome="the two chat models have a credential and the red warning is gone from both.">

A short detour into the Credentials page. n8n stores secrets encrypted and never shows them again in full, and it selects a credential for you on any node when exactly one of the right type exists.

- In the left sidebar, open Overview, then the Credentials tab, then Create credential. <Shot src="/posts/digital-branch-concierge/n8n-steps/03-credentials-create.png" alt="The Credentials tab with the Create credential button highlighted." caption="Overview, Credentials, Create credential" />
- Search for DeepSeek, paste your API key from platform.deepseek.com, name it and save. The demo uses deepseek-flash. <Shot src="/posts/digital-branch-concierge/n8n-steps/03-deepseek-credential.png" alt="The n8n DeepSeek credential dialog with the API Key field highlighted, the key masked and Connection tested successfully." caption="The DeepSeek credential" />
- Back in the main process, open Guardrails model and Agent model and confirm the credential is selected. <Shot src="/posts/digital-branch-concierge/n8n-steps/03-deepseek-models.png" alt="The Agent model node open in n8n, with DeepSeek account selected as the credential and deepseek-flash as the model." caption="DeepSeek selected on Agent model" />

</ProcessStep>

<ProcessStep title="Connect Slack, both sides" outcome="a Slack channel with the app in it, an n8n credential that passes its test and both approval nodes ready.">

Slack is where the two human decisions happen. The setup has a Slack side and an n8n side, and the order matters. n8n's own pages for this are the [Slack credential guide](https://docs.n8n.io/integrations/builtin/credentials/slack/) and the [Slack approvals guide](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.slack/approvals/).

- **Create the Slack app.** Go to [api.slack.com/apps](https://api.slack.com/apps), choose Create New App, From scratch, name it (the demo calls it n8n integration) and pick the workspace you control. <Shot src="/posts/digital-branch-concierge/n8n-steps/04-slack-create-app.png" alt="The Slack Create new app dialog with the AI agent, Starter app, From a manifest and Blank app choices." caption="Create the app" />
- **Add the bot scopes.** Under OAuth & Permissions, Bot Token Scopes, add chat:write (post messages), chat:write.public (post to public channels the bot has not joined), channels:read and groups:read (resolve a channel by name), users:read and users:read.email (name and email of the person who clicked). The screenshot also shows a few extra scopes left over from earlier testing. The six above are all this build needs. <Shot src="/posts/digital-branch-concierge/n8n-steps/04-slack-scopes.png" alt="The Scopes section of the Slack app's OAuth & Permissions page, listing the bot token scopes." caption="The bot token scopes" />
- **Install the app to the workspace** with the Install to Workspace button on the same page, then copy the Bot User OAuth Token (it starts with xoxb). Every time you add a scope later, reinstall the app, or Slack keeps the old permissions.
- **Copy the signing secret** from Settings, Basic Information, App Credentials. n8n uses it to check that an approval really came from Slack. <Shot src="/posts/digital-branch-concierge/n8n-steps/04-slack-signing-secret.png" alt="The Slack app's Basic Information page with the App Credentials section: App ID, Client ID, Client Secret and Signing Secret fields." caption="Basic Information, Signing Secret" />
- **Enable Interactivity.** Under Interactivity & Shortcuts switch it on and set the Request URL to your instance followed by /webhook-waiting-slack, for example https://your-name.app.n8n.cloud/webhook-waiting-slack, with no trailing slash, characters or spaces. A browser visit to that URL shows 404, which is expected: Slack sends it a signed POST. Save. <Shot src="/posts/digital-branch-concierge/n8n-steps/04-slack-interactivity.png" alt="The Interactivity & Shortcuts page with Interactivity on and the Request URL ending in webhook-waiting-slack." caption="Interactivity on, Request URL set" />
- **Create the channel.** In Slack, Add channels, Create a new channel, name it concierge-approvals and Create. A public channel keeps the demo simple. For anything real, make it private and invite only the decision owners.
- **Restrict who can approve, for anything real.** On Human decision (Slack), fill in Restrict Who Can Approve with the named decision owners. n8n documents that an empty list lets anyone who can see the message approve or decline. The pre-action approval uses signed links while n8n issue 37692 is open, so anyone who has the link could act on it, which is another reason to keep that channel private.
- **Add the app to the channel.** In the new channel use Add people or agents, type the app's name and Add. The join message names both you and the app.
- **Create the n8n credential.** Back in n8n, Credentials, Create credential, search Slack API, paste the bot token into Access Token and the signing secret into Signature Secret, name it (the demo uses Slack (concierge approvals)) and save. The dialog tests the connection. <Shot src="/posts/digital-branch-concierge/n8n-steps/04-n8n-slack-credential.png" alt="The n8n Slack API credential dialog with Access Token and Signature Secret filled and Connection tested successfully." caption="The n8n Slack credential" />
- **Check the two nodes.** In the main process open Pre-action approval (Slack) and Human decision (Slack): the credential is selected and the channel is #concierge-approvals by name. On Human decision (Slack), Capture Who Responded is on, with After Decision set to Show Outcome and Remove Buttons. Pre-action approval keeps Capture Who Responded off for now: with it on, human review tool nodes currently return 404 when a reviewer clicks, a known issue with a fix in review ([n8n issue 37692](https://github.com/n8n-io/n8n/issues/37692)). So its buttons are signed links back to n8n, and the responder is not captured for that step yet. <Shot src="/posts/digital-branch-concierge/n8n-steps/04-n8n-human-decision.png" alt="The Human decision (Slack) node with Capture Who Responded on and After Decision set to Show Outcome and Remove Buttons." caption="Human decision (Slack) settings" />
- **Create the decisions table.** Overview, Data tables, Create data table, name it Concierge human decisions and add the columns case_id, execution_id, decision_point, proposed_action, approved (boolean), responded_at, responder_id, responder_name, responder_email, channel_id, message_id, context_shown and recorded_at. Select it in the Record decision node. <Shot src="/posts/digital-branch-concierge/n8n-steps/04-n8n-decisions-table.png" alt="The Concierge human decisions Data Table with its thirteen columns." caption="The human decisions table" />
- **Symptoms and what they mean.** "This app responded with status code 404" on a button: the Request URL is wrong, or Capture Who Responded is on for the pre-action node. "channel_not_found": the channel does not exist, or the app is not in it. Buttons that stay after a click: that node has Capture Who Responded off, so n8n cannot edit the message, and a second click gets "No action required". The Slack desktop and web clients can lag behind the API by minutes. The messages are there, as the n8n execution log shows.
- **No Slack?** Swap both nodes for any send-and-wait node, such as Gmail or the n8n Form. The gate logic does not change.

</ProcessStep>

### Review

<ProcessSteps start={6}>

<ProcessStep title="Read a skill before you run it" outcome="you can point at the node that stops a risky action before it happens.">

The skills are where the pre-action gate lives, and they are short enough to read in a minute.

- Open Concierge skill: Print statement. The trigger declares three typed inputs: account_id, period_months and session_customer_id. <Shot src="/posts/digital-branch-concierge/n8n-steps/06-skill-canvas.png" alt="The Print statement skill on the canvas: When Executed by Another Workflow, Check authorisation, Authorised?, then Do the work and Result on the true branch and Refused on the false branch." caption="The Print statement skill on the canvas" />
- Open Check authorisation, the first node after the trigger. It looks the account up in the embedded customer table and refuses if the account does not belong to the identified customer, before anything else runs. <Shot src="/posts/digital-branch-concierge/n8n-steps/06-skill-check-authorisation.png" alt="The Check authorisation code node open, showing the refuse function and the ownership check." caption="The authorisation check" />
- Follow the Authorised? branch to Do the work and Result. The result carries the text plus risk and status back to the process.
- Now open Concierge skill: Update contact details. Its shape is the same, and the approval is not inside it. Back in the main process, the update_contact_details tool connects to Pre-action approval (Slack), n8n's human review step, and that node connects to the agent. The agent's proposed call pauses there until a decision owner approves, and only then does the skill run.

</ProcessStep>

<ProcessStep title="Follow the outer process" outcome="you can trace where accountability, containment and lineage each sit on the canvas.">

The main process is the deterministic wrapper. Read it left to right once before running anything.

- Identify customer stands in for the photo ID check at the counter and picks the customer for the session, C1003 by default. <Shot src="/posts/digital-branch-concierge/n8n-steps/07-main-canvas.png" alt="The main process canvas, tidied and zoomed to fit, with the agent and its tools in the middle and the gate on the right." caption="The outer process" />
- Guardrails in runs the jailbreak and topical-alignment checks. Its Fail output goes to a fixed Refusal, never back into the agent.
- The AI Agent holds the conversation with seven tools: the four skills, two read-only Code Tools and the knowledge search.
- Guardrails out strips card numbers, IBANs and secret keys from the reply.
- Assemble facts, a Code node with no model in it, builds what the gate reads: the highest risk any skill returned, the customer's open complaint and vulnerability flags, and policy keywords in the request.

</ProcessStep>

<ProcessStep title="Check the gate fails safe" outcome="only an explicit, positive classification reaches the customer directly.">

This is the setting the whole safety argument rests on.

- Open Impact and policy gate, a Switch node. It has two rules: straight_through and refused. <Shot src="/posts/digital-branch-concierge/n8n-steps/08-gate-location.png" alt="The main process canvas zoomed in, with the Impact and policy gate highlighted to the right of Assemble facts and its Straight through, Refused and Review outputs." caption="Where the Impact and policy gate sits" />
- Look at the fallback output, renamed Review. Anything that matches neither rule, including a missing or unrecognised classification, goes to a person. <Shot src="/posts/digital-branch-concierge/n8n-steps/08-gate-node.png" alt="The Impact and policy gate node open, with the straight_through rule and the fallback output renamed Review highlighted." caption="The gate's fallback is Review" />
- Follow the Review output to Human decision (Slack): a send-and-wait with two buttons, Send to customer and Hold and hand over. The message shows the request, why the gate fired, which skills ran and the proposed reply.

</ProcessStep>

</ProcessSteps>

### Run it

<ProcessSteps start={9}>

<ProcessStep title="Run the test conversations" outcome="one execution per test conversation, with the route each one took and the reasons the gate gave.">

Now the evidence. Each conversation is designed to exercise one of the five concerns on the scorecard.

- Click Open chat on the main process and send the conversations on this page, one at a time. <Shot src="/posts/digital-branch-concierge/n8n-steps/09-chat-and-logs.png" alt="The editor with the chat panel on the left and the logs panel on the right after a test conversation." caption="Chat and logs side by side" />
- Tag a message with [customer:C1001] to switch to the customer with an open complaint, or [customer:C1002] for the vulnerable customer. <Shot src="/posts/digital-branch-concierge/n8n-steps/09-chat-customer-tag.png" alt="The n8n chat box with a message ending in [customer:C1001], the tag highlighted." caption="A message tagged with a customer" />
- To find a run later, open the Executions tab, click Filters and set Highlighted data to key test_id, tick Exact match and enter the test id as the value, for example T05. Identify customer tags every run with customer_id and Assemble facts adds route, so you can also filter by customer or by route, such as review. A test message pasted as it appears on this page is matched to its test id automatically, while your own messages carry customer_id and route only. If the agent asks you to confirm, add the tag to your reply, for example "Yes, that is correct [test:T06]", so the run that follows keeps the test id. The tag is removed before the agent sees the message. Filtering by highlighted data needs n8n Cloud Pro or Enterprise, or a self-hosted Enterprise or registered Community edition. On other plans, filter by status and start time instead, or note the execution id shown in the logs after each run. <Shot src="/posts/digital-branch-concierge/n8n-steps/09-executions-filter.png" alt="The Executions tab with the Filters panel open, Highlighted data set to key test_id with Exact match ticked and value T05, narrowing the list to a single run." caption="Filter executions by test_id" />
- For each run, open the execution in the Executions tab and step through it: every node shows what went in and what came out, including the agent's tool calls and the token counts.
- Note who approved in Slack, and what they saw. That is the accountability evidence.

</ProcessStep>

<ProcessStep title="Run them as an evaluation" outcome="a pass rate you can rerun after every change.">

The same conversations, run as a set, give the drift evidence.

- Create a Data Table named Concierge test conversations from the test-conversations CSV in the repository. Its columns are test_id, message, customer_id, expected_route, expected_skill and note (id is a reserved column name in Data Tables, hence test_id). <Shot src="/posts/digital-branch-concierge/n8n-steps/10-eval-create-table.png" alt="The n8n Create new data table dialog named Concierge test conversations, with Import CSV selected, an upload area and My CSV file contains a header row ticked." caption="Create the table with Import CSV" /> <Shot src="/posts/digital-branch-concierge/n8n-steps/10-eval-table.png" alt="The Concierge test conversations Data Table with twelve rows, T01 to T12, and the test_id column highlighted." caption="The imported table, with test_id" />
- Open When running evaluation in the main process and select that table. <Shot src="/posts/digital-branch-concierge/n8n-steps/10-eval-trigger-table.png" alt="The When running evaluation node open, with Source set to Data table and Concierge test conversations selected and highlighted." caption="Select the table on When running evaluation" />
- Run the evaluation. ### Potential findings

These are early observations from initial testing on a limited number of runs on one n8n cloud instance. I may have missed a setting or misread a result, so treat them as things to check on your own instance rather than settled conclusions.

<ScrollCards label="Four potential findings from initial testing" hint="Scroll through the four findings">

<ScrollCard number="01" title="A tool call with missing arguments reached the reviewer">

On n8n cloud 2.39.4 the model once proposed update_contact_details with no arguments, and the reviewer was asked to approve that empty call. As far as I could tell, the tool's schema check rejected it only after approval. If that holds, checking the call before a person sees it would keep every approval meaningful.

</ScrollCard>

<ScrollCard number="02" title="Item references after a resume">

After the review resumed, node references written as "the item from node X" could no longer trace their item link. n8n documents this as expected item-linking behaviour, and "the first item from node X" worked in this build.

</ScrollCard>

<ScrollCard number="03" title="Memory carried between customers">

This one most likely came from my own configuration. The balance question, run straight after the vulnerable customer's email change, came back with a remark about "your email change" under the other customer's name. I had keyed Simple Memory by the chat session, and the demo switches customers inside one session. Keying memory by the identified customer as well as the session stopped it in my runs, and that change is now in the build.

</ScrollCard>

<ScrollCard number="04" title="Evaluation runs appeared to share memory">

Also likely my configuration. Evaluation sessions reused the same ids, so run 2 seemed to be partly answering from run 1's memory. They now carry the execution id.

</ScrollCard>

Each looked small, and none would have shown up without the test conversations.

Where this build would need to grow is governance at scale. The gate's rules live inside this workflow, in a Code node and a Switch node, and each skill carries its own authorisation check. For one concierge that is clear and easy to review. Across a portfolio of agents it becomes hard to keep consistent. Every workflow holds its own copy of the rules, so changing what counts as a vulnerable customer or a lending request means finding and editing each copy, and two agents can quietly treat the same customer differently. The rules are not a governed artefact in their own right either. A risk owner cannot read or approve them without opening a workflow, an auditor sees them only as node settings, and nothing stops a new skill being connected without the authorisation check at the top.

The answer is architectural rather than a missing feature. Put the policy in one place every agent calls, such as a shared policy sub-workflow or a decision table in a policy engine, then version it and approve changes to it once. Start every skill from a template that already contains the authorisation check. n8n then does what it does best, orchestrating the process and the agent, while the rules that decide what needs a person are owned, tested and changed centrally. n8n makes the sandwich quick to build. Keeping every sandwich the same across dozens of agents is the part to design for.

## Conclusion

Can a low-code platform give an agent room to act without handing it final authority? On this build, yes, as long as the boundaries are designed deliberately. Routine requests went straight through. The higher-impact ones paused for a person. The execution log kept enough evidence to reconstruct why, node by node. The evaluation set also caught configuration faults that a smooth demonstration would have hidden, including memory crossing customer and test-run boundaries.

What stayed with me was how visible the design remained. A business analyst, process owner and engineer can stand at the same canvas and point at the skill, the gate or the human decision they are arguing about. The pieces a governed agent needs are already in the product: bounded sub-workflows, a human review step, guardrails, Data Tables, execution history and evaluations. None of them made the first working version harder to reach.

The score of 8 out of 10 reflects that foundation. The opportunity is governance at portfolio scale, keeping policy rules, authorisation patterns and approval evidence consistent when one agent becomes dozens. That is architecture around n8n rather than inside it: policy held in one governed place, skill templates reused, rule changes versioned and evaluations that cover the human steps as well as the automated ones.

The build left me more confident about n8n for governed agentic automation. It makes the sandwich quick to assemble and easy to explain, and it gives three disciplines somewhere practical to meet. The test now is whether those strengths hold as the agents multiply. The freedom in the middle is only ever as safe as the process around it.
