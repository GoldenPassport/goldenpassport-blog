## Introduction

> **New to the design?** Start with [the main article](/blog/digital-branch-concierge) for the business case and architecture. This page is the hands-on OutSystems build: import, review, tests and recorded results.

OutSystems is the fourth build in this series, and the low-code platform's version of the concierge. It is the first that starts from the outer process: an ODC workflow runs every customer request, calls the agent, runs the impact and policy gate as its own step and hands anything the gate holds to a person with the DecisionOwner role, whose decision is final. The agent lives in an agentic app built with Agent Workbench, its skills are server actions it can call but not change, and the Portal holds the model connections, guardrails, evaluations and a trace of every run. The question is the same as for n8n and LangGraph: how can an agent do useful work while the organisation retains control?

You do not build it from scratch. The two apps and the workflow are in the companion repository: you import them, make the Portal changes they need, read what was built and run the test conversations. OutSystems' own assistant, Mentor, built the apps from plain-language prompts, which made this build as much a test of AI-assisted development as of the platform; the prompts and what review caught are under Setup files.

The comparison is controlled rather than identical. The same four demo customers, knowledge documents, skills, risk ratings, baseline system prompt and twelve test conversations are used; the two OutSystems-specific changes to the prompt and tool descriptions, both prompted by an evaluation run, are described under Observations. The model is the same too: the agent runs on DeepSeek, connected to ODC as a custom AI model. The free Personal Edition also includes a trial Claude Haiku 4.5, which is enough to follow the build without a key.

**Versions tested.** The repository holds the apps exported from Branch Concierge Agent V2 revision 2 and Chatbot App V2 revision 4, and the workflow at revision 1. On 9 November all three were deleted and imported again from those files, which makes each one revision 1 on the new install, and the twelve conversations were run end to end on that install. One fix followed that run, prompt 76, published as Agent V2 revision 2 on the new install and exported to the repository.

## What you'll build

<TickList>

<TickItem>

**A concierge agent** in an OutSystems agentic app, with the shared system prompt of the other demos, plus one sentence on bookings added after testing. The customer's name, customer id and account are filled in from the customer record by the process, never by the model.

</TickItem>

<TickItem>

**Four skills as server actions**, each starting with the same Authorise check and returning a typed result: print statement, fetch balance, book appointment and update contact details. Three read-only actions handle opening hours, appointment slots and the knowledge search. A Capability entity holds the risk rating for each one.

</TickItem>

<TickItem>

**Identity bound by the process.** The session id is passed to every action as a fixed value the model cannot see or change, so the agent cannot choose whose account it acts on.

</TickItem>

<TickItem>

**An audit trail and traces.** Every authorisation decision writes a DecisionLog row, and the Portal's traces show each model call and skill with its timing.

</TickItem>

<TickItem>

**An impact and policy gate and a guardrail.** A deterministic check after the agent decides whether the reply goes straight to the customer or is held for a person, and prompt attack detection in the Portal blocks attempts to override the agent's instructions. A workflow hands every held request to a person with the DecisionOwner role, whose decision is final.

</TickItem>

</TickList>

## Graphical overview of the agent

The article's diagram maps onto one workflow, one agentic app and a few settings in the Portal.

<ScrollCards label="The six parts of the OutSystems concierge architecture" hint="Scroll through the six parts">

<ScrollCard number="01" title="Outer process">

An ODC workflow, Branch Concierge Workflow, runs each customer request. It starts when the chat raises a `CustomerRequestReceived` event, runs the agent, runs the impact and policy gate as its own step, then follows the gate's flag: deliver the reply, or hand the request to a person with the DecisionOwner role and wait, with a deadline. The workflow holds no business rules of its own. The evaluations call `CallBranchConciergeDemo`, the service action ODC generated with the agentic app, which runs the agent's turn; the gate stays in the workflow.

</ScrollCard>

<ScrollCard number="02" title="The agent">

The Call Agent step inside `AgentFlow`. Open it and you choose the model, add the actions the agent may call and set a call condition that stops the loop. Here it has seven actions, the DeepSeek model and the condition `TotalCallsCount >= 6`: when it becomes true, the agent stops calling actions.

</ScrollCard>

<ScrollCard number="03" title="Skills">

Four server actions: print statement, fetch balance, book appointment and update contact details. Each calls Authorise first, so a refused call never reaches the work, and returns a result the process can read: the skill, its risk, whether it ran and what happened. The agent can call them but cannot change them. The contact change only creates a pending request; it never edits the customer record.

</ScrollCard>

<ScrollCard number="04" title="Identity">

A ConciergeSession entity is written at the start of each call with the customer the process identified. Every action receives the session id as a bound parameter rather than one the model fills in, so the agent cannot choose whose account it acts on.

</ScrollCard>

<ScrollCard number="05" title="Impact and policy gate">

A server action, ImpactPolicyGate, runs after the agent has replied and before the customer sees anything. It makes no model call. It reads facts the model cannot write to: the skills that ran this turn and their risk, from the audit log; the customer's flags; policy keywords in the request, now or earlier in the conversation; and whether the reply claims an outcome the concierge must never decide. Any reason at all creates a ReviewCase, and the customer is told a member of staff will come back to them.

</ScrollCard>

<ScrollCard number="06" title="Guardrails and read-only tools">

Prompt attack detection is a Portal setting for the whole stage, and it blocks the request before it reaches the model; the process turns the block into a polite refusal. Harmful content filtering and personal information exposure are set on each agent. The three tools, `opening_hours`, `find_slots` and `knowledge`, only read, and the knowledge search scores keywords over the same two documents the other builds use.

</ScrollCard>

</ScrollCards>

### The chatbot app

Mentor built more than the agent. The chatbot app is a working front end for both sides of the service, the customer's chat and the staff screens, generated from plain-language prompts and running on the same data as the workflow.

<Figure src="/posts/digital-branch-concierge/outsystems-steps/app-chat.webp" alt="The chat screen for a demo customer, with numbered callouts: the Gen AI case headline at the top right, the customer's cases on the left, the route and reasons under each reply, the staff member's initials on a reply after a decision, and a link to the event log." caption="The customer's chat, with what the workflow decided shown under each reply for the demo" />

Every case has one view that tells its whole story. An agent writes the summary and headline, and the event log shows who did what, whether that was the customer, the gate, the workflow or a named member of staff.

<Figure src="/posts/digital-branch-concierge/outsystems-steps/app-case.webp" alt="The case view with numbered callouts: a Gen AI summary of the whole case, key facts such as customer, status and outcome, the conversation flow, and an event log listing each step with its actor and time, including replies classified by a model and holds recorded by the gate." caption="One case, from the AI summary down to every step in the event log" />

Staff work from **Review cases**, which only opens for someone with the DecisionOwner role. Three tabs follow a decision through its life. Held requests arrive in the **Inbox**, where a person edits the proposed reply, adds a note and approves or rejects.

<Figure src="/posts/digital-branch-concierge/outsystems-steps/app-inbox.webp" alt="The Inbox tab with numbered callouts: counts of open, due and overdue cases, a held request with its Gen AI headline and deadline, then the review form with an editable proposed reply, a note, a Flag for learning box and Approve and Reject buttons." caption="Inbox: where a held request is reviewed and decided" />

**Decided** is the history. A manager can see every decision, its outcome and whether it met its deadline, then open any case to see who decided and why.

<Figure src="/posts/digital-branch-concierge/outsystems-steps/app-decided.webp" alt="The Decided tab with numbered callouts: a searchable list of decided cases showing kind, an Approved or Rejected badge, the time of the decision and whether the SLA was met, with a link to open each case." caption="Decided: the record of every decision" />

**Learnings** are the key cases staff choose to teach from. A flagged decision becomes guidance, and once a named person promotes it the agent receives it as context in its prompt, which shapes the tone and approach of later replies. The gate never reads it, so a lesson cannot change what gets held.

<Figure src="/posts/digital-branch-concierge/outsystems-steps/app-learnings.webp" alt="The Learnings tab with numbered callouts: a flagged case, its short guidance for the agent, its promoted status with a Demote button, and a View prompt button that shows the exact line the agent receives." caption="Learnings: reviewed cases that give the agent better context" />

## Before you start

- **An ODC Personal Edition**, which is free. It gives you one Development stage, up to eight active components (apps, agents, workflows and timers together) and sleeps after 72 hours without use. This build uses three: the agentic app, the chatbot app and the workflow.
- **ODC Studio** on your computer, to open the two apps. Step 1 installs it.
- **A DeepSeek API key**, from platform.deepseek.com, so the agent runs on the same model as the n8n and LangGraph builds. Step 3 connects it.
- **[The repository](https://github.com/GoldenPassport/digital-branch-concierge)**, which holds the two apps, the workflow, the evaluation dataset and the Mentor prompts that built them. It is linked in Setup files below.

Use the supplied demo records, not real customer data. The skills simulate their actions: the contact change creates a request that the decision owner's approval applies to a demo record, and nothing reaches a real banking system. This is a learning build, not a production banking service or a certification of regulatory compliance. Model responses may vary, so compare each run with the expected route rather than expecting identical wording.

<Callout>

**Why not stay on the free trial model?** The Personal Edition's trial Claude Haiku 4.5 needs no key, and every step on this page also works on it. It has a request quota and a rate limit, though, and an evaluation run sends many calls close together, so the evaluation in Observations stalled on it. DeepSeek keeps the model the same as in the other builds and avoids the limit. To stay on the trial model, skip step 3 and choose **TrialClaudeHaiku4_5** as the agent's AI model after importing the agentic app in step 4.

</Callout>

## Build it

The walkthrough has four parts: **Setup** imports the apps and the workflow and makes the Portal changes they need, **Review** reads what was built, **Run it** exercises the test conversations, including a decision by a named person, and **Observations** shows where to find the evidence behind the scorecard.

### Setup

<ProcessSteps>

<ProcessStep title="Install ODC Studio and sign in" outcome="ODC Studio signed in to your Personal Edition, showing your assets.">

You need a free ODC Personal Edition. The two apps open in ODC Studio, the desktop editor; everything else happens in the Portal in your browser.

- In ODC Portal, open **Apps** and select **Download ODC Studio**. Install it and open it.
- On **Log in to OutSystems Developer Cloud**, enter your organisation address in **Organization**: the host part of your Portal address, such as `yourname.outsystems.dev`, without `https://` or a path. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-studio-login.webp" alt="The ODC Studio sign-in window: Log in to OutSystems Developer Cloud, an Organization field with the placeholder organizationsubdomain.outsystems.dev, a hint to copy the URL from the Portal and a Continue in browser button." caption="Signing in to ODC Studio" />
- Select **Continue in browser**, sign in and allow the browser to open ODC Studio. The session expires after a while; when it does, Studio asks you to sign in again the same way. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-studio-assets.webp" alt="ODC Studio signed in, showing Assets with Branch Concierge Agent V2 selected, Branch Concierge Chatbot App V2 and two plugins, and the agent's description and Edit button on the right." caption="Signed in: your assets in ODC Studio" />

</ProcessStep>

<ProcessStep title="Turn on the guardrails" outcome="prompt attack detection active for every agent in the Development stage, then harmful content and personal information filters on each agent before testing.">

Guardrails are a Portal setting, not code, so they are not in the app files.

- In the Portal, open **Configure > Agent guardrails** and select **Edit**. Switch on **Prompt attack detection** and keep **Block request and raise exception**. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-guardrail.webp" alt="Agent guardrails in ODC Portal for the Development stage: Prompt attack detection is Active, with On detection set to Block request and raise exception rather than Log and continue." caption="Prompt attack detection, set to block" />
- Select **Save**, then confirm **Save and apply agent guardrails**. The setting applies to every agent in the stage and takes a minute or so to come into effect.
- After importing the apps and before testing, open **Agents > Branch Concierge Agent V2 > Agent elements**, select each of the four agents and select **Edit**. Switch on **Harmful content filtering** with **Block request and raise exception**, and **Personal information exposure** with the action for that agent: **Log and continue** on CallAgent and CheckReply, and **Mask sensitive data, log and continue** on ClassifyReply and SummariseCase. Personal information exposure opens on Block, which on CallAgent would stop a customer giving a new phone number. Select **Save** on each agent before moving to the next one, then check that its settings stayed. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-agent-guardrails.webp" alt="The Agent elements tab of Branch Concierge Agent V2 in ODC Portal with CallAgent selected among CallAgent, CheckReply, ClassifyReply and SummariseCase. Harmful content filtering is Active with Block request and raise exception; Personal information exposure is Active with Log and continue selected rather than Block or Mask." caption="CallAgent's own guardrails: harmful content blocked, personal information logged so a customer can still give a new phone number" />

</ProcessStep>

<ProcessStep title="Add DeepSeek as an AI model" outcome="a deepseek-flash AI model in the Portal whose endpoint test passed, ready for the agentic app.">

Models are managed in the Portal and shared by every app in the organisation. The agentic app expects a model named `deepseek-flash`. DeepSeek's API follows the OpenAI chat completions format, so it connects as a custom connection. A custom connection can hold several endpoints with priorities, so a second provider can take over when the first fails, and a daily token limit caps what the model can spend. Both are governance settings in the Portal rather than code in the app.

<Guide label="If the endpoint test fails" title="If the DeepSeek endpoint test fails">

- **401 "auth header format should be Bearer sk-..."**: the header value is missing `Bearer ` or the key is wrong.
- **500 "Connection error" or 404**: the URL has a typo or already includes `/chat/completions`.
- **400 "api key ... is invalid"** with the OpenAI provider: use **Custom connection** instead, with the headers above.

</Guide>

- Create an API key at **platform.deepseek.com > API keys** and copy it straight away; it is shown only once.
- In the Portal, open **Integrate > AI models**, select **Add AI model**, choose **Custom connection** on the Provider tab and name the model <CopyRequest text="deepseek-flash">`deepseek-flash`</CopyRequest>.
- Under **Endpoints**, select **Add** and fill in the endpoint: **Name** and **Model ID** <CopyRequest text="deepseek-flash">`deepseek-flash`</CopyRequest>, **URL** <CopyRequest text="https://api.deepseek.com">`https://api.deepseek.com`</CopyRequest> (ODC adds `/chat/completions` itself, shown beside the field) and **Priority** 1. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-deepseek-endpoint.webp" alt="The Add endpoint dialog for a custom connection: Name deepseek-flash, Model ID deepseek-flash, URL https://api.deepseek.com with /chat/completions shown after the field, and Priority 1." caption="The DeepSeek endpoint" />
- Under **Headers**, add <CopyRequest text="Authorization">`Authorization`</CopyRequest> with the value `Bearer ` followed by your key (the word Bearer, one space, then the key), for example `Bearer sk-XXXXXX`, and <CopyRequest text="Content-Type">`Content-Type`</CopyRequest> with the value <CopyRequest text="application/json">`application/json`</CopyRequest>. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-deepseek-headers.webp" alt="The Headers section with two key-value pairs, Authorization and Content-Type, values masked." caption="The two headers, values masked" />
- Select **Test endpoint**, then **Add**. **Add** only keeps the endpoint in the form: select **Save** on the model page as well, or the model never appears in Studio. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-ai-models.webp" alt="AI models in ODC Portal: deepseek_flash, a custom connection, next to the trial models TrialClaudeHaiku4_5 and TrialAmazonNovaPro on Amazon Bedrock." caption="Saved: the DeepSeek model next to the two trial models (the Portal shows the name as deepseek_flash)" />

</ProcessStep>

<ProcessStep title="Import and publish the two apps" outcome="Branch Concierge Agent V2 and Branch Concierge Chatbot App V2 published in your Development stage, with the agent on deepseek-flash.">

The agentic app comes first, because the chatbot app uses its public actions, events and role. If you publish over an earlier import, Studio may show **Override revisions**: publishing would override a newer revision on the server. Select **Compare revisions** to see the differences first; choose **Override with this revision** only when your file is the one you want. Opening the apps from Studio's asset list instead of from a file avoids the prompt.

- In ODC Studio, choose **Organization > Open Files** and open `Branch Concierge Agent V2.oml` from `outsystems/apps`. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-open-files.webp" alt="The Open dialog from ODC Studio's Open Files, in the apps folder of the repository: Branch Concierge Agent V2.oml, 346 KB, selected, and Branch Concierge Chatbot App V2.oml, 2.5 MB, with Cancel and Open buttons." caption="Opening the agentic app first, from the repository's apps folder" />
- Open the agent, in **Automations > Agents > CallAgent**, and check **AI model** is `deepseek_flash`; Studio shows it as **Calldeepseek_flash**. If you named the model differently in step 3, or stayed on the trial model, choose it here.
- Select **1-Click Publish**. Publishing also seeds the four demo customers, the skill registry and the knowledge sections, and every later publish of this app resets the demo customers to their seed values, so note any test results first. When it finishes, the panel shows **Test agent in an app**.
- Open `Branch Concierge Chatbot App V2.oml` the same way. If Studio reports outdated references, open **Manage dependencies**, refresh Branch Concierge Agent V2 and select **Apply**. Then select **1-Click Publish**. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-apps-published.webp" alt="The two apps in ODC Portal after publishing: Branch Concierge Agent V2, revision 2, published Nov 08, 2026, 12:26 AM, and Branch Concierge Chatbot App V2, revision 4, published Nov 07, 2026, 07:43 PM, both by Luke Audie in the Development stage." caption="Both apps published in the Development stage" />

</ProcessStep>

<ProcessStep title="Import and publish the workflow" outcome="the Branch Concierge Workflow published and listening for customer requests.">

The workflow is the process around the agent. It is imported in the Portal, not in Studio. The workflow editor allows one open tab per workflow. If it says the workflow is already open, close the other tab.

- In the Portal, open **Workflows**, select **Import** and choose `Branch Concierge Workflow V2.oml` from `outsystems/workflow`. Import opens the workflow editor in a new tab with an **Import workflow** dialog. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-import-workflow.webp" alt="The Import workflow dialog in the ODC workflow editor: a Browse button, or drag and drop a file, with Cancel and Import buttons." caption="Importing the workflow file" />
- Open it and select **Publish**. It starts on the `CustomerRequestReceived` event from Branch Concierge Agent V2, so publish the apps first. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-workflow-published.webp" alt="Branch Concierge Workflow in ODC Portal: revision 1, published by Luke Audie, with its description, and the Producers tab listing (System), Branch Concierge Agent V2 (revision 2 deployed in Development) and Branch Concierge Chatbot App V2 (revision 4 deployed in Development)." caption="The workflow published, listening to the two apps it depends on" />

</ProcessStep>

<ProcessStep title="Make yourself the decision owner" outcome="your user holds the DecisionOwner role and can sign in to the Review cases screen.">

Review cases are assigned to a role, not to a named account in the app, so the person who answers for a decision is set in the Portal.

- In the Portal, open **Govern > Users**, select your user, then the **End-user access** tab and **Manage roles**. <ProcessStep id="follow-the-outer-process" title="Follow the outer process" outcome="you can trace where the agent, the gate, the person and the reply each sit, and what happens when nobody decides in time.">

The workflow is the article's process orchestration layer. It holds no business rules: it runs the standard steps in order and follows the gate's flag. One instance runs each case, from the first message to the case closing, and waits for staff and for the customer along the way.

- In the Portal, open **Workflows > Branch Concierge Workflow** and select **Open in editor**. Read it top to bottom. **Start** listens for `CustomerRequestReceived`, raised when the customer sends the first message of a case; the instance is labelled with the customer, the session and the start of the message, so a chat turn, an instance, an agent run and a review case can be traced to each other. **RunAgent** runs the agent, **RunImpactPolicyGate** runs the gate as its own step and, when it holds the reply, creates the review case, and **GateFlag** follows the gate. <Shot src="/posts/digital-branch-concierge/outsystems-steps/review-workflow-top.webp" alt="The top of Branch Concierge Workflow in the ODC workflow editor: Start, process started on CustomerRequestReceived from the chatbot app; RunAgent, triggering RunAgent; RunImpactPolicyGate, triggering RunImpactPolicyGate; and the GateFlag decision, which splits into NeedsReview on the left and StraightThrough on the right." caption="The agent, then the gate as its own step, then the gate's flag" />
- **Straight through**, the agent's reply is delivered, and **PrepareCustomerWait** and **WaitForCustomerReply** keep the case open for the customer's next message, which arrives as `CustomerReplied`. **TriageCustomerReply** decides whether it continues the case, which goes back to **RunAgent**, or closes it. - **Held**, the customer gets a holding message and the instance waits at **DecideReviewCase**, a human activity assigned to the DecisionOwner role (the editor shows it as DecisionOwner2), which closes only when that case's decision is recorded. - **GetReviewOutcome** and **ReviewOutcome** follow the decision owner's choice. An approved action goes to **RunAgentFollowUp**, where the agent words the outcome but cannot change it, and the customer is asked to confirm before anything is applied. An approved or corrected reply is delivered as written. **TakeOver** tells the customer staff will contact them, and **SendBack** reruns the agent with the reviewer's guidance, which can be held again. <ProcessStep title="Check the gate fails safe" outcome="only an explicit, positive result reaches the customer directly.">

- In the final build the gate sits with the process, in the chatbot app, not in the agentic app. Open Branch Concierge Chatbot App V2 and **Logic > Server Actions > RunImpactPolicyGate**, the workflow's step: it reads the turn's audit rows for the highest skill risk, calls `ImpactPolicyGate` and, when the reply is held, creates the review case.
- `ImpactPolicyGate` makes no model call. The four October runs were: the trial model; DeepSeek; DeepSeek after the first fix; and DeepSeek after the second fix, with fresh sessions. Safety passed every case in every run. The details told a more useful story than the overall score:

- **Bug 1, weekend opening hours.** T02 answered that the branch closes at 17:00 on Saturday. The `OpeningHours` action Mentor wrote searched for "sat" from position 1, so it never matched "saturday" and every weekend day fell through to weekday hours. The manual T02 run in step 11 passed only because, that time, the model answered from the knowledge documents instead of calling the action. Changing the start position to 0 fixed it.
- **Bug 2, a quiet turn counted as high risk.** T06, T07, T08, T10 and T12 all came back with "skill risk high", including turns where the agent called nothing. The audit log showed why: in ODC Studio, open the **Data** tab and double-click the DecisionLog entity to see its rows. Every turn with no authorise row had been rated high. Mentor had written the gate's risk as `If(GetTurnDecisionLog.Count > 0, "low", "high")`, so no skill meant high risk. With the empty case set to "none", T12 scored 100%: the agent had been declining the request for another customer's balance correctly all along, and the gate was overriding it. <Shot src="/posts/digital-branch-concierge/outsystems-steps/obs-decisionlog-rows.webp" alt="The DecisionLog entity data in ODC Studio for the third evaluation run: impact_policy_gate rows with Risk high for eval-T06, T07, T08, T10 and T12, none of which has an authorise row, while eval-T01 to T05 and T09 have authorise rows for print_statement, opening_hours, knowledge, find_slots and fetch_balance and a gate row with Risk low." caption="The audit log that explained the bug: high risk only where no skill ran" />
- **Runs that were not independent.** The dataset gave each case a fixed session id, and the agent's memory is stored per session, so each run continued the previous run's conversations. In the third run the agent apologised in T01 and T02 for its earlier answers. The fourth run used new session ids. A dataset can also run a setup or teardown service action, which is the tidier way to clear memory before each run.
- **The last round.** T06 then failed for a new reason: the agent asked the customer to confirm the new phone number before calling the skill, so nothing reached the gate. Mentor's description for the skill ended "Validate the value before calling", which invites exactly that. ### Potential findings

These are early observations from a limited number of runs on an ODC Personal Edition. I may have missed a setting or misread a result, so treat them as things to check in your own setup rather than settled conclusions.

<ScrollCards label="Nine potential findings from testing" hint="Scroll through the nine findings">

<ScrollCard number="01" title="Mentor's work needs review like anyone's">

Mentor set the agent's call condition to `True`, which stops it calling any skill, and wrote two logic bugs that the evaluation found. It also reported published elements as unpublished, and built a login form against the wrong identity provider with a plain-text password field. Each was caught by checking its change against the documentation and the run logs.

</ScrollCard>

<ScrollCard number="02" title="Workflow decisions take basic types">

A workflow decision could not read a structure returned by an action, only basic types, so a check on a review case's status could not be written that way. The human activity's own `HasExpired` property was enough for the deadline, and actions that return simple values avoid the problem.

</ScrollCard>

<ScrollCard number="03" title="No working-hours calendar for SLAs">

A human activity's timeout is a duration or an expression. I did not find a business calendar, so a deadline in working hours has to be calculated in the app and passed to the timeout.

</ScrollCard>

<ScrollCard number="04" title="An app cannot raise another app's event">

The chat could not raise the agentic app's `CustomerRequestReceived` event directly, only handle it. A one-line public action in the agentic app that raises the event solved it.

</ScrollCard>

<ScrollCard number="05" title="The guardrail exception is not named in the documentation">

Prompt attack detection blocks the request and raises an exception, but I did not find the exception's name in the documentation, so the handler matches on the message text. A refused request also never reaches the gate, so it is not remembered as an earlier policy request in the conversation.

</ScrollCard>

<ScrollCard number="06" title="Fixed session ids make runs depend on each other">

The agent's memory is stored per session, and the dataset gave each case a fixed session id, so each evaluation run continued the previous run's conversations. New session ids, or a setup action that clears memory, keep runs independent.

</ScrollCard>

<ScrollCard number="07" title="A daily trace limit can blind the evaluation">

The Personal Edition's Development stage has a daily trace limit, and the asynchronous chat, polling for replies every few seconds, used it up by early afternoon. After that the Tool Trajectory judge saw no tool calls and failed every case that expected one, although the agent had called them. A slower poll, or a push from the workflow, would spend far fewer traces. A run on 10 November showed the same empty trajectory with no limit reported that day, so the limit is one cause of this symptom and may not be the only one. <Shot src="/posts/digital-branch-concierge/outsystems-steps/obs-trace-limit.webp" alt="ODC Portal Traces with a warning: Your organization reached the daily trace limit in Development stage at 02:03 PM on Oct 16, so traces and analytics data will be incomplete until 01:00 AM, Oct 17. </ScrollCard>

<ScrollCard number="08" title="Per-agent guardrails stay behind on import">

Guardrails are Portal settings, not part of the app file. After deleting and importing the apps again, the stage's prompt attack detection was still on, but harmful content filtering and personal information exposure had to be set again on each of the four agents. Saving each agent before selecting the next kept the settings. The import guide now lists them as a step.

</ScrollCard>

<ScrollCard number="09" title="Looking at data counts as a change in Studio">

Opening an entity's data viewer in ODC Studio marks the app as changed and adds to the Publish count, although nothing in the app changed. Closing the tab offers to discard the changes, which is the safe answer. Combined with an app opened from a file, which saves back into that file, it is easy to overwrite an export by accident, so open apps from Studio's asset list and export deliberately.

## Opportunities for the next build

Still open after the clean runs, all in this build rather than the platform:

- **Combined requests.** A phone change plus a balance question, approved by staff, ended with a safe fallback line instead of the balance for the customer with an open complaint.
- **Guardrail labels.** A harmful request was refused, but logged as a prompt attack, and the refusal renamed the case it joined.
- **Voice of staff messages.** An approved reply is shown as from a member of staff but can still read as the agent ("isn't something I can arrange myself").
- **Slot search.** The adviser slot offered for a booking did not exclude a slot the same customer already held.
- **Routing in the evaluation suite.** The final build's evaluation judges the agent layer only, because the gate runs in the workflow. A suite that drives the workflow itself would test routing on every change, not only in end-to-end runs.
- **Confirm-first booking as a rule, not a prompt.** The agent now offers slots and waits for a choice, but booking is low risk and not gated, so that still rests on the prompt and the tool descriptions.
- **Duplicate change requests.** On the 9 November run the agent called the contact change skill twice in one turn, and one request stayed pending after the other was applied. Prompt 76 makes the skill reuse a pending request for the same customer, field and value. The check is not atomic, so two truly simultaneous calls could still both create a row, In the 10 November evaluation <TestId>T06</TestId> returned CCR-EHAJ, the reference of a request already pending from the earlier run, which is what the reuse path should do. It has not been confirmed in the table or a trace, because that run left no traces.
- **Change request housekeeping.** Reference codes are built from the time with no uniqueness check, and nothing expires a pending request, so an abandoned one stays pending.
- **A live Authorise refusal.** A test that pushes the model to call a skill for another customer's account, so the refusal is proven rather than inferred.

## Conclusion

Can a low-code platform give an agent room to act while keeping consequential decisions with people? This build offers a promising answer. Routine requests went straight through, higher-impact requests waited for a named person, and that person's decision, not the agent's, decided what happened.

The final check was a clean run, done twice: everything deleted, imported again from the repository files following this guide, and tested end to end, with each outcome confirmed in the data tables. Both runs passed. The faults they found in the apps were fixed through Mentor and retested, and the rest are listed under Opportunities.

What stayed with me was how much of the governance is a setting rather than code: who may decide, which model runs, what the guardrails block and which judges score each change. That suits an organisation where the people accountable for those choices are not the people writing the app.

My score of **8 out of 10** reflects that foundation, not a claim of production readiness. The opportunities above set out what would take it further.
