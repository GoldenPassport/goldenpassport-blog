## Introduction

> **New to the design?** Start with [the main article](/blog/digital-branch-concierge) for the business case and architecture. This page is the hands-on OutSystems build: setup, tests and recorded results.

OutSystems is the fourth build in this series, and the low-code platform's version of the concierge. The agent lives in an agentic app built with Agent Workbench in ODC Studio, its skills are server actions the agent can call but not change, and the Portal holds the model connections, guardrails, evaluations and a trace of every run. OutSystems' own assistant, Mentor, did most of the building from plain-language requests, which made this build as much a test of AI-assisted development as of the platform. The question is the same as for n8n and LangGraph: how can an agent do useful work while the organisation retains control?

The comparison is controlled rather than identical. The same four demo customers, knowledge documents, skills, risk ratings, system prompt and twelve test conversations are used. The model is the same too: the agent runs on DeepSeek, connected to ODC as a custom AI model. The free Personal Edition also includes a trial Claude Haiku 4.5, which is enough to follow the build without a key.

## What you'll build

<TickList>

<TickItem>

**A concierge agent** in an OutSystems agentic app, using the same system prompt used for the other demos. The customer's name, customer id and account are filled in from the customer record by the process, never by the model.

</TickItem>

<TickItem>

**Four skills as server actions**, each starting with the same Authorise check and returning a typed result: print statement, fetch balance, book appointment and update contact details. Three read-only actions handle opening hours, appointment slots and the knowledge search. A Capability entity holds the risk rating for each one.

</TickItem>

<TickItem>

**Identity bound by the process.** The session id is passed to every action as a fixed value the model cannot see or change, so the agent cannot choose whose account it acts on.

</TickItem>

<TickItem>

**An audit trail and traces.** Every authorisation decision writes a DecisionLog row, and the Portal's traces show each model call and skill with its timing.

</TickItem>

<TickItem>

**An impact and policy gate and a guardrail.** A deterministic check after the agent decides whether the reply goes straight to the customer or is held for a person, and prompt attack detection in the Portal blocks attempts to override the agent's instructions. **TODO:** the review workflow with a named decision owner and the evaluation run.

</TickItem>

</TickList>

## Graphical overview of the agent

The article's diagram maps onto one service action, one agent and a few settings in the Portal.

<ScrollCards label="The six parts of the OutSystems concierge architecture" hint="Scroll through the six parts">

<ScrollCard number="01" title="Outer process">

When you create an agentic app, OutSystems Developer Cloud (ODC) generates a service action, `CallBranchConcierge`, and inside it an `AgentFlow` with five steps: get grounding data, build the messages, call the model, store the memory and return the response. The process around the agent lives in `CallBranchConcierge`: it records who the customer is, calls the agent, then runs the gate before anything reaches the customer.

</ScrollCard>

<ScrollCard number="02" title="The agent">

The Call Agent step inside `AgentFlow`. Open it and you choose the model, add the actions the agent may call and set a call condition that stops the loop. Here it has seven actions, the DeepSeek model and the condition `TotalCallsCount >= 6`: when it becomes true, the agent stops calling actions.

</ScrollCard>

<ScrollCard number="03" title="Skills">

Four server actions: print statement, fetch balance, book appointment and update contact details. Each calls Authorise first, so a refused call never reaches the work, and returns a result the process can read: the skill, its risk, whether it ran and what happened. The agent can call them but cannot change them. The contact change only creates a pending request; it never edits the customer record.

</ScrollCard>

<ScrollCard number="04" title="Identity">

A ConciergeSession entity is written at the start of each call with the customer the process identified. Every action receives the session id as a bound parameter rather than one the model fills in, so the agent cannot choose whose account it acts on.

</ScrollCard>

<ScrollCard number="05" title="Impact and policy gate">

A server action, ImpactPolicyGate, runs after the agent has replied and before the customer sees anything. It makes no model call. It reads facts the model cannot write to: the skills that ran this turn and their risk, from the audit log; the customer's flags; policy keywords in the request, now or earlier in the conversation; and whether the reply claims an outcome the concierge must never decide. Any reason at all creates a ReviewCase, and the customer is told a member of staff will come back to them.

</ScrollCard>

<ScrollCard number="06" title="Guardrails and read-only tools">

Prompt attack detection is a Portal setting for the whole stage, and it blocks the request before it reaches the model; the process turns the block into a polite refusal. opening_hours, find_slots and knowledge only read, and the knowledge search scores keywords over the same two documents the other builds use.

</ScrollCard>

</ScrollCards>

## Before you start

- **An ODC Personal Edition**, which is free. It gives you one Development stage, up to eight active components (apps, agents, workflows and timers together) and sleeps after 72 hours without use. This build uses two so far: the agentic app and the generated test app.
- **ODC Studio** on your computer. Agents are built in Studio; Mentor Web in the Portal builds web apps only.
- **A DeepSeek API key**, from platform.deepseek.com, so the agent runs on the same model as the n8n and LangGraph builds. Step 3 connects it.
- **Prefer to skip the build?** The finished apps are in the [companion repository](https://github.com/GoldenPassport/digital-branch-concierge/tree/main/outsystems/oml) as two files: `outsystems/oml/Branch Concierge Demo.oml`, the agentic app, and `outsystems/oml/Branch Concierge Demo test app.oml`, its chat test app. In ODC Studio, choose **Organization > Open Files**, open the agentic app first, select **1-Click Publish**, then do the same for the test app. You still need the prompt attack guardrail and the DeepSeek model in your own Portal: the agentic app expects an AI model named `deepseek-flash`, so do steps 2 and 3 first. If you name yours differently, or stay on the trial model, choose it under **AI model** in the agent after opening the file.

<Callout>

**Why not stay on the free trial model?** The Personal Edition's trial Claude Haiku 4.5 needs no key, and every step on this page also works on it. It has a request quota and a rate limit, though, and an evaluation run sends many calls close together, so the evaluation in Observations stalled on it. Switching to DeepSeek early keeps the model the same as in the other builds and avoids the limit. If you would rather start on the trial model, skip step 3, choose **TrialClaudeHaiku4_5** in step 4 and switch later: the agent's model can be changed at any time.

</Callout>

## Build it

The walkthrough has five parts: **Setup** prepares ODC Studio, the guardrail, the model and the agentic app, **Build** creates the concierge with Mentor, **Review** checks what Mentor built, **Run it** exercises the test conversations and **Observations** shows where to find the evidence behind the scorecard.

### Setup

<ProcessSteps>

<ProcessStep title="Install ODC Studio and sign in" outcome="ODC Studio signed in to your Personal Edition, showing your assets.">

You need a free ODC Personal Edition. Agents are built in ODC Studio, the desktop editor; everything else in this walkthrough happens in the Portal in your browser.

- In ODC Portal, open **Apps** and select **Download ODC Studio**. Install it and open it.
- On **Log in to OutSystems Developer Cloud**, enter your organisation address in **Organization**: the host part of your Portal address, such as `yourname.outsystems.dev`, without `https://` or a path. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-studio-login.webp" alt="The ODC Studio sign-in window: Log in to OutSystems Developer Cloud, an Organization field with the placeholder organizationsubdomain.outsystems.dev, a hint to copy the URL from the Portal and a Continue in browser button." caption="Signing in to ODC Studio" />
- Select **Continue in browser**, sign in and allow the browser to open ODC Studio. The session expires after a while; when it does, Studio asks you to sign in again the same way.

</ProcessStep>

<ProcessStep title="Turn on the prompt attack guardrail" outcome="prompt attack detection active for every agent in the Development stage.">

Guardrails are a Portal setting, not code, so switch this one on before you build.

- In the Portal, open **Configure > Agent guardrails** and select **Edit**. Switch on **Prompt attack detection** and keep **Block request and raise exception**. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-guardrail.webp" alt="Agent guardrails in ODC Portal for the Development stage: Prompt attack detection is Active, with On detection set to Block request and raise exception rather than Log and continue." caption="Prompt attack detection, set to block" />
- Select **Save**, then confirm **Save and apply agent guardrails**. The setting applies to every agent in the stage and takes a minute or so to come into effect.

</ProcessStep>

<ProcessStep title="Add DeepSeek as an AI model" outcome="a deepseek-flash AI model in the Portal whose endpoint test passed, ready to choose in Studio.">

Models are managed in the Portal and shared by every app in the organisation. DeepSeek's API follows the OpenAI chat completions format, so it connects as a custom connection.

- Create an API key at **platform.deepseek.com > API keys** and copy it straight away; it is shown only once.
- In the Portal, open **Integrate > AI models**, select **Add AI model**, choose **Custom connection** on the Provider tab and give the model a name.
- Under **Endpoints**, select **Add** and fill in the endpoint: **Name** and **Model ID** `deepseek-flash`, **URL** `https://api.deepseek.com` (ODC adds `/chat/completions` itself, shown beside the field) and **Priority** 1. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-deepseek-endpoint.webp" alt="The Add endpoint dialog for a custom connection: Name deepseek-flash, Model ID deepseek-flash, URL https://api.deepseek.com with /chat/completions shown after the field, and Priority 1." caption="The DeepSeek endpoint" />
- Under **Headers**, add `Authorization` with the value `Bearer ` followed by your key (the word Bearer, one space, then the key), for example `Bearer sk-XXXXXX`, and `Content-Type` with the value `application/json`. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-deepseek-headers.webp" alt="The Headers section with two key-value pairs, Authorization and Content-Type, values masked." caption="The two headers, values masked" />
- Select **Test endpoint**, then **Add**. **Add** only keeps the endpoint in the form: select **Save** on the model page as well, or the model never appears in Studio.

<Guide label="If the endpoint test fails" title="If the DeepSeek endpoint test fails">

- **401 "auth header format should be Bearer sk-..."**: the header value is missing `Bearer ` or the key is wrong.
- **500 "Connection error" or 404**: the URL has a typo or already includes `/chat/completions`.
- **400 "api key ... is invalid"** with the OpenAI provider: use **Custom connection** instead, with the headers above.

</Guide>

A custom connection can hold several endpoints with priorities, so a second provider can take over when the first fails, and a daily token limit caps what the model can spend. Both are governance settings in the Portal rather than code in the app.

</ProcessStep>

<ProcessStep title="Create the agentic app" outcome="an agentic app on DeepSeek, with the service action and AgentFlow that ODC generates.">

- In Studio, open the arrow beside **Create** and choose **Agentic app**. Give it a name and a short description. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-agentic-app.webp" alt="The Enter your agentic app details dialog with an app icon, the name Branch Concierge Demo and the description: digital branch concierge, answers from bank knowledge, calls bounded skills, hands decisions to a person." caption="The agentic app details" />
- Choose **deepseek_flash**, the model from step 3, and select **Create agentic app**. The trial models on Amazon Bedrock are listed beside it and need no key. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-choose-model.webp" alt="The Choose an AI model dialog listing deepseek_flash, TrialAmazonNovaPro and TrialClaudeHaiku4_5, with deepseek_flash selected and a Create agentic app button." caption="Choosing the DeepSeek model" />
- ODC generates a service action named after the app, here `CallBranchConcierge`, with a single AgentFlow step. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-generated-service-action.webp" alt="A freshly generated service action in ODC Studio: Start, AgentFlow, Response and End, with the Logic tab listing the service action, the REST integration and the app's role." caption="The generated service action" />
- Double-click **AgentFlow** to see the agent's own flow: get grounding data, build the messages, call the model, store the memory, return the response. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-agentflow.webp" alt="The generated AgentFlow in ODC Studio: Start, GetGroundingData, BuildMessages, CallTrialClaudeHaiku4_5, StoreMemory, Response and End, each with a help note, and the Logic tab listing the generated server actions AIModels, BuildMessages, GetGroundingData, LoadMemory and StoreMemory." caption="Evidence: the AgentFlow ODC generates, before Mentor adds anything" />
- Studio names the agent after the model you chose, and the name stays if you switch models later. Rename it so it does not depend on the model: in **Automations > Agents**, select the agent and change **Name** to `CallAgent`. The screenshots on this page were taken before the rename, so they show the original name, `CallTrialClaudeHaiku4_5`.

</ProcessStep>

</ProcessSteps>

### Build

Mentor is the AI assistant inside Studio, behind the sparkle icon at the top right. Six prompts build the concierge from the same specification as the other builds. Open each one from its step to read it, adjust it and copy it; the files are also in the [companion repository](https://github.com/GoldenPassport/digital-branch-concierge/tree/main/outsystems/mentor-prompts) under `outsystems/mentor-prompts`. Send them in order, one at a time, wait for each to finish, select **Publish**, then check **Portal > Logs** for errors before the next: a publish can succeed while the logic still fails at run time. Mentor on the Personal Edition has a daily usage limit; the six prompts fit in a day, but fix-up requests on top can run it out.

### Review

Mentor did most of the work. One of its choices on the first build is worth checking in any AI-assisted build, because it quietly switched the agent's tools off. The prompt in the repository now includes the fix.

<ProcessSteps start={9}>

<ProcessStep title="Set the agentic loop limit" outcome="a loop limit that stops the agent after six calls, not one that stops it calling at all.">

Mentor first set the call condition to `True` and explained that a hard limit on the number of calls could not be expressed. OutSystems' documentation says the opposite on both points: when the condition is true, the agent stops calling actions, and `TotalCallsCount`, `LoopCount` and `TokenUsage` are there for exactly this purpose. Left as it was, the agent could not have called any skill. The fix is one line: `TotalCallsCount >= 6`. <Shot src="/posts/digital-branch-concierge/outsystems-steps/build-call-condition.webp" alt="Action calling settings in the agent editor with the Call Condition set to TotalCallsCount >= 6." caption="The loop limit, TotalCallsCount >= 6" />

</ProcessStep>

</ProcessSteps>

The lesson is not that the assistant is unreliable. It built the data model, nine server actions and the agent wiring in about twenty minutes. The lesson is that its output needs the same review as anyone else's, against the documentation and the run logs, before a customer sees it.

The four runs were: the trial model; DeepSeek; DeepSeek after the first fix; and DeepSeek after the second fix, with fresh sessions. Safety passed every case in every run. The details told a more useful story than the overall score:

- **Bug 1, weekend opening hours.** T02 answered that the branch closes at 17:00 on Saturday. The `OpeningHours` action Mentor wrote searched for "sat" from position 1, so it never matched "saturday" and every weekend day fell through to weekday hours. The manual T02 run in step 10 passed only because, that time, the model answered from the knowledge documents instead of calling the action. Changing the start position to 0 fixed it.
- **Bug 2, a quiet turn counted as high risk.** T06, T07, T08, T10 and T12 all came back with "skill risk high", including turns where the agent called nothing. The audit log showed why: in ODC Studio, open the **Data** tab and double-click the DecisionLog entity to see its rows. Every turn with no authorise row had been rated high. Mentor had written the gate's risk as `If(GetTurnDecisionLog.Count > 0, "low", "high")`, so no skill meant high risk. With the empty case set to "none", T12 scored 100%: the agent had been declining the request for another customer's balance correctly all along, and the gate was overriding it. <Shot src="/posts/digital-branch-concierge/outsystems-steps/obs-decisionlog-rows.webp" alt="The DecisionLog entity data in ODC Studio for the third evaluation run: impact_policy_gate rows with Risk high for eval-T06, T07, T08, T10 and T12, none of which has an authorise row, while eval-T01 to T05 and T09 have authorise rows for print_statement, opening_hours, knowledge, find_slots and fetch_balance and a gate row with Risk low." caption="The audit log that explained the bug: high risk only where no skill ran" />
- **Runs that were not independent.** The dataset gave each case a fixed session id, and the agent's memory is stored per session, so each run continued the previous run's conversations. In the third run the agent apologised in T01 and T02 for its earlier answers. The fourth run used new session ids. A dataset can also run a setup or teardown service action, which is the tidier way to clear memory before each run.
- **The last round.** T06 then failed for a new reason: the agent asked the customer to confirm the new phone number before calling the skill, so nothing reached the gate. Mentor's description for the skill ended "Validate the value before calling", which invites exactly that. The description now uses the shared wording plus one sentence: call the skill as soon as the customer gives the new value, because the approval step checks it. This is the one place where the OutSystems build adds to the shared specification, and an evaluation run is why. The dataset was also corrected where it was stricter than the specification: T01's expected reply no longer needs the account number, T02 expects the opening hours lookup, and T10 expects no skill call because the customer never gives the new email address.

## What this build shows

TODO once the gate, workflow and evaluation are in place. Points so far:

- The sandwich maps naturally onto ODC: workflow outside, agent inside, skills as server actions it can call but not change.
- Binding the session id as a fixed action parameter keeps identity out of the model's hands, without middleware.
- There is no hook that runs before every action call, so pre-action authorisation lives at the top of each skill.
- Observability comes built in: traces, per-agent analytics and logs, without adding a separate tracing product.
- The policy gate is ordinary deterministic logic after the agent, and it is fast: 7 ms in the T06 trace.
- Guardrails are a Portal setting rather than code, which suits a governance team, but the application still has to handle the block itself, and the exception is not named in the documentation.
- One behaviour differs from LangGraph: a request refused by the guardrail never reaches the gate, so it is not remembered as an earlier policy request in the conversation. Defensible, since the request was refused, but worth knowing.
