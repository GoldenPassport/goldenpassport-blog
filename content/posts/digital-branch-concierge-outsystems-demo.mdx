## Introduction

> **New to the design?** Start with [the main article](/blog/digital-branch-concierge) for the business case and architecture. This page is the hands-on OutSystems build: setup, tests and recorded results.

OutSystems is the fourth build in this series, and the low-code platform's version of the concierge. The agent lives in an agentic app built with Agent Workbench in ODC Studio, its skills are server actions the agent can call but not change, and the Portal holds the model connections, guardrails, evaluations and a trace of every run. OutSystems' own assistant, Mentor, did most of the building from plain-language requests, which made this build as much a test of AI-assisted development as of the platform. The question is the same as for n8n and LangGraph: how can an agent do useful work while the organisation retains control?

The comparison is controlled rather than identical. The same four demo customers, knowledge documents, skills, risk ratings, system prompt and twelve test conversations are used. The main difference is the model: the earlier builds used DeepSeek, and here the agent runs on the trial Claude Haiku 4.5 that comes with the free Personal Edition, for a reason explained below.

## What you'll build

<TickList>

<TickItem>

**A concierge agent** in an OutSystems agentic app, using the same system prompt used for the other demos. The customer's name, customer id and account are filled in from the customer record by the process, never by the model.

</TickItem>

<TickItem>

**Four skills as server actions**, each starting with the same Authorise check and returning a typed result: print statement, fetch balance, book appointment and update contact details. Three read-only actions handle opening hours, appointment slots and the knowledge search. A Capability entity holds the risk rating for each one.

</TickItem>

<TickItem>

**Identity bound by the process.** The session id is passed to every action as a fixed value the model cannot see or change, so the agent cannot choose whose account it acts on.

</TickItem>

<TickItem>

**An audit trail and traces.** Every authorisation decision writes a DecisionLog row, and the Portal's traces show each model call and skill with its timing.

</TickItem>

<TickItem>

**An impact and policy gate and a guardrail.** A deterministic check after the agent decides whether the reply goes straight to the customer or is held for a person, and prompt attack detection in the Portal blocks attempts to override the agent's instructions. **TODO:** the review workflow with a named decision owner and the evaluation run.

</TickItem>

</TickList>

## Graphical overview of the agent

The article's diagram maps onto one service action, one agent and a few settings in the Portal.

<ScrollCards label="The six parts of the OutSystems concierge architecture" hint="Scroll through the six parts">

<ScrollCard number="01" title="Outer process">

When you create an agentic app, OutSystems Developer Cloud (ODC) generates a service action, `CallBranchConcierge`, and inside it an `AgentFlow` with five steps: get grounding data, build the messages, call the model, store the memory and return the response. The process around the agent lives in `CallBranchConcierge`: it records who the customer is, calls the agent, then runs the gate before anything reaches the customer.

</ScrollCard>

<ScrollCard number="02" title="The agent">

The Call Agent step inside `AgentFlow`. Open it and you choose the model, add the actions the agent may call and set a call condition that stops the loop. Here it has seven actions, the trial Claude Haiku 4.5 model and the condition `TotalCallsCount >= 6`: when it becomes true, the agent stops calling actions.

</ScrollCard>

<ScrollCard number="03" title="Skills">

Four server actions: print statement, fetch balance, book appointment and update contact details. Each calls Authorise first, so a refused call never reaches the work, and returns a result the process can read: the skill, its risk, whether it ran and what happened. The agent can call them but cannot change them. The contact change only creates a pending request; it never edits the customer record.

</ScrollCard>

<ScrollCard number="04" title="Identity">

A ConciergeSession entity is written at the start of each call with the customer the process identified. Every action receives the session id as a bound parameter rather than one the model fills in, so the agent cannot choose whose account it acts on.

</ScrollCard>

<ScrollCard number="05" title="Impact and policy gate">

A server action, ImpactPolicyGate, runs after the agent has replied and before the customer sees anything. It makes no model call. It reads facts the model cannot write to: the skills that ran this turn and their risk, from the audit log; the customer's flags; policy keywords in the request, now or earlier in the conversation; and whether the reply claims an outcome the concierge must never decide. Any reason at all creates a ReviewCase, and the customer is told a member of staff will come back to them.

</ScrollCard>

<ScrollCard number="06" title="Guardrails and read-only tools">

Prompt attack detection is a Portal setting for the whole stage, and it blocks the request before it reaches the model; the process turns the block into a polite refusal. opening_hours, find_slots and knowledge only read, and the knowledge search scores keywords over the same two documents the other builds use.

</ScrollCard>

</ScrollCards>

## Before you start

- **An ODC Personal Edition**, which is free. It gives you one Development stage, up to eight active components (apps, agents, workflows and timers together) and sleeps after 72 hours without use. This build uses two so far: the agentic app and the generated test app.
- **ODC Studio** on your computer. Agents are built in Studio; Mentor Web in the Portal builds web apps only.
- **No model key at first.** The Personal Edition includes trial models on Amazon Bedrock for the Development stage. This build uses TrialClaudeHaiku4_5.

<Callout>

**Why not DeepSeek?** The n8n and LangGraph builds used DeepSeek. ODC supports models it does not list natively through a Custom connection, but the published contract for that connection carries chat messages only, with no tool definitions or tool calls. An agent that has to call skills needs tool calling, so this build uses a natively supported model instead. {/* TODO: confirm with a test before publishing. */}

</Callout>

## Build it

### Setup

1. In ODC Portal, open **Apps** and select **Download ODC Studio**. Install it and open it.
2. On **Log in to OutSystems Developer Cloud**, enter your organisation address in **Organization**: the host part of your Portal address, such as `yourname.outsystems.dev`. Select **Continue in browser** and sign in.
3. In Studio, open **Create**, choose **Agentic app**, name it `Branch Concierge` and add a short description.
4. Choose the AI model. The trial models appear here; this build uses **TrialClaudeHaiku4_5**. Select **Create agentic app**.

### Building with Mentor

Mentor is the AI assistant inside Studio (the sparkle icon at the top right). Each part of the concierge was built from one plain-language request, using the specification from the LangGraph build:

| Request | What Mentor built | Time |
| --- | --- | --- |
| Customer entity and the four demo customers | Entity, bootstrap action and a timer to seed it | 4 min 16 s |
| Registry, audit log, appointments, contact changes, knowledge | Five entities, the seven capabilities and eleven knowledge sections | 1 min 16 s |
| Authorise, four skills, three tools, wired to the agent | Session entity, nine server actions, seven agent actions with the session id bound | 12 min 43 s |
| System prompt from the customer record | Two lookups before the messages are built; the prompt word for word | 59 s |
| Replace every SQL query with entity actions | See below | 3 min 56 s |
| Impact and policy gate, review cases | Gate server action, ReviewCase entity, held reply | 2 min 34 s |
| Fix the knowledge search | Word scoring instead of a whole-phrase match | 2 min 19 s |
| Turn a guardrail block into a refusal | Three attempts; see below | 1 to 3 min each |

After about ten requests in one day, several of them large, Mentor reported that it had reached its usage limit, with a reset in just under 14 hours. Plan the build around that on the Personal Edition.

### Review

Mentor did most of the work, and two of its choices needed correcting. Both were easy to fix once found, and both are worth checking in any AI-assisted build.

<Accordion title="The call condition">

Mentor set the agent's call condition to `True` and explained that a hard limit on the number of calls could not be expressed. OutSystems' documentation says the opposite on both points: when the condition is true, the agent stops calling actions, and `TotalCallsCount`, `LoopCount` and `TokenUsage` are available for exactly this purpose. Left as it was, the agent would have been unable to call any skill. The fix was one line: `TotalCallsCount >= 6`.

</Accordion>

<Accordion title="The SQL that never ran">

The first publish succeeded with only minor warnings, but the first conversation failed. The Portal's **Logs** showed why: Mentor had written SQL with column names the database did not recognise, so the session lookup failed on every call and the seed data had never been written. A second request asked Mentor to replace every SQL query with entity actions and lookups, which is the more idiomatic approach in OutSystems anyway. After republishing, the trace showed the seed action complete in just over a second.

</Accordion>

<Accordion title="The knowledge search that matched nothing">

The first run of T03 answered "I don't have that information in our documents", although the Mortgages section says exactly what to bring. Mentor's own diagnosis was that its search looked for the entire question as a single phrase inside each section, so a full question never matched. The rewrite scores each section by how many of the question's words it contains, as in the n8n and LangGraph builds, and T03 then passed.

</Accordion>

<Accordion title="Catching the guardrail">

With prompt attack detection set to block, the agent call fails with an exception, and the process should turn that into a polite refusal. Mentor first caught a User Exception, then a Communication Exception; neither matched, and the documentation does not name the exception. The log line did: "Failed to call AI model ... Guardrail violation: Prompt attack detection". The fix that worked was a catch-all handler that checks the message for "Guardrail violation", takes the refused path when it finds it, and raises anything else again so other errors are not hidden.

</Accordion>

The lesson is not that the assistant is unreliable. It built the data model, nine server actions and the agent wiring in about twenty minutes. The lesson is that its output needs the same review as anyone else's, against the documentation and the run logs, before a customer sees it.

### Observations

- **Every run is traced.** In the Portal, **Agents**, then the agentic app, then **Go to analytics** shows requests, response times, errors and the slowest requests, and each request opens a trace with every step and its timing.
- **The gates are cheap.** In the T02 trace, the opening hours action, including the Authorise check and the audit write, took 11 ms. Looking up the session and the customer and loading the memory took a few milliseconds more.
- **The model call dominates.** In the same trace, the first model call took 50.2 s and the second, with the same prompt and actions, 2.4 s. The T05 run took 10.2 s end to end. Response times on the trial model varied widely from run to run. {/* TODO: more samples before drawing a conclusion; compare with a paid model connection. */}
- **Long runs hit the screen's timeout.** One T01 run was still waiting on the model after about 60 seconds, and the test app's server call was cancelled. A second run passed.
- **A whole turn is cheap apart from the model.** In the T06 trace (6.2 s in total), the contact change skill took 37 ms, including Authorise and creating the pending request, and the impact and policy gate took 7 ms, including creating the review case. Later in the day, turns took between 3 and 8 seconds.
- **The guardrail is clearly logged.** When prompt attack detection blocked T11, the Portal's Logs recorded "Guardrail violation: Prompt attack detection. Input blocked (Prompt Attack)". A guardrail change takes a moment to apply: the first T11 run, straight after saving, reached the agent and was caught by the policy gate instead.
- **Replies use markdown.** The model's bold text appears with its asterisks in the test app. A line in the prompt or a renderer in the UI would fix it.

## What this build shows

TODO once the gate, workflow and evaluation are in place. Points so far:

- The sandwich maps naturally onto ODC: workflow outside, agent inside, skills as server actions it can call but not change.
- Binding the session id as a fixed action parameter keeps identity out of the model's hands, without middleware.
- There is no hook that runs before every action call, so pre-action authorisation lives at the top of each skill.
- Observability comes built in: traces, per-agent analytics and logs, without adding a separate tracing product.
- The policy gate is ordinary deterministic logic after the agent, and it is fast: 7 ms in the T06 trace.
- Guardrails are a Portal setting rather than code, which suits a governance team, but the application still has to handle the block itself, and the exception is not named in the documentation.
- One behaviour differs from LangGraph: a request refused by the guardrail never reaches the gate, so it is not remembered as an earlier policy request in the conversation. Defensible, since the request was refused, but worth knowing.
