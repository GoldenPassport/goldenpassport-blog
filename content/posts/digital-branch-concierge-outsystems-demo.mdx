## Introduction

> **New to the design?** Start with [the main article](/blog/digital-branch-concierge) for the business case and architecture. This page is the hands-on OutSystems build: import, review, tests and recorded results.

OutSystems is the fourth build in this series, and the low-code platform's version of the concierge. It is the first that starts from the outer process: an ODC workflow runs every customer request, calls the agent, runs the impact and policy gate as its own step and hands anything the gate holds to a person with the DecisionOwner role, whose decision is final. The agent lives in an agentic app built with Agent Workbench, its skills are server actions it can call but not change, and the Portal holds the model connections, guardrails, evaluations and a trace of every run. The question is the same as for n8n and LangGraph: how can an agent do useful work while the organisation retains control?

You do not build it from scratch. The two apps and the workflow are in the companion repository: you import them, make the Portal changes they need, read what was built and run the test conversations. OutSystems' own assistant, Mentor, built the apps from plain-language prompts, which made this build as much a test of AI-assisted development as of the platform; the prompts and what review caught are under Setup files.

The comparison is controlled rather than identical. The same four demo customers, knowledge documents, skills, risk ratings, system prompt and twelve test conversations are used. The model is the same too: the agent runs on DeepSeek, connected to ODC as a custom AI model. The free Personal Edition also includes a trial Claude Haiku 4.5, which is enough to follow the build without a key.

## What you'll build

<TickList>

<TickItem>

**A concierge agent** in an OutSystems agentic app, using the same system prompt used for the other demos. The customer's name, customer id and account are filled in from the customer record by the process, never by the model.

</TickItem>

<TickItem>

**Four skills as server actions**, each starting with the same Authorise check and returning a typed result: print statement, fetch balance, book appointment and update contact details. Three read-only actions handle opening hours, appointment slots and the knowledge search. A Capability entity holds the risk rating for each one.

</TickItem>

<TickItem>

**Identity bound by the process.** The session id is passed to every action as a fixed value the model cannot see or change, so the agent cannot choose whose account it acts on.

</TickItem>

<TickItem>

**An audit trail and traces.** Every authorisation decision writes a DecisionLog row, and the Portal's traces show each model call and skill with its timing.

</TickItem>

<TickItem>

**An impact and policy gate and a guardrail.** A deterministic check after the agent decides whether the reply goes straight to the customer or is held for a person, and prompt attack detection in the Portal blocks attempts to override the agent's instructions. A workflow hands every held request to a person with the DecisionOwner role, whose decision is final.

</TickItem>

</TickList>

## Graphical overview of the agent

The article's diagram maps onto one workflow, one agentic app and a few settings in the Portal.

<ScrollCards label="The six parts of the OutSystems concierge architecture" hint="Scroll through the six parts">

<ScrollCard number="01" title="Outer process">

An ODC workflow, ConciergeRequest, runs each customer request. It starts when the chat raises a `CustomerRequestReceived` event, runs the agent, runs the impact and policy gate as its own step, then follows the gate's flag: deliver the reply, or hand the request to a person with the DecisionOwner role and wait, with a deadline. The workflow holds no business rules of its own. The evaluations call `CallBranchConcierge`, the service action ODC generated with the agentic app, which runs the same agent and gate in one call.

</ScrollCard>

<ScrollCard number="02" title="The agent">

The Call Agent step inside `AgentFlow`. Open it and you choose the model, add the actions the agent may call and set a call condition that stops the loop. Here it has seven actions, the DeepSeek model and the condition `TotalCallsCount >= 6`: when it becomes true, the agent stops calling actions.

</ScrollCard>

<ScrollCard number="03" title="Skills">

Four server actions: print statement, fetch balance, book appointment and update contact details. Each calls Authorise first, so a refused call never reaches the work, and returns a result the process can read: the skill, its risk, whether it ran and what happened. The agent can call them but cannot change them. The contact change only creates a pending request; it never edits the customer record.

</ScrollCard>

<ScrollCard number="04" title="Identity">

A ConciergeSession entity is written at the start of each call with the customer the process identified. Every action receives the session id as a bound parameter rather than one the model fills in, so the agent cannot choose whose account it acts on.

</ScrollCard>

<ScrollCard number="05" title="Impact and policy gate">

A server action, ImpactPolicyGate, runs after the agent has replied and before the customer sees anything. It makes no model call. It reads facts the model cannot write to: the skills that ran this turn and their risk, from the audit log; the customer's flags; policy keywords in the request, now or earlier in the conversation; and whether the reply claims an outcome the concierge must never decide. Any reason at all creates a ReviewCase, and the customer is told a member of staff will come back to them.

</ScrollCard>

<ScrollCard number="06" title="Guardrails and read-only tools">

Prompt attack detection is a Portal setting for the whole stage, and it blocks the request before it reaches the model; the process turns the block into a polite refusal. opening_hours, find_slots and knowledge only read, and the knowledge search scores keywords over the same two documents the other builds use.

</ScrollCard>

</ScrollCards>

## Before you start

- **An ODC Personal Edition**, which is free. It gives you one Development stage, up to eight active components (apps, agents, workflows and timers together) and sleeps after 72 hours without use. This build uses three: the agentic app, the test app and the workflow.
- **ODC Studio** on your computer, to open the two apps. Step 1 installs it.
- **A DeepSeek API key**, from platform.deepseek.com, so the agent runs on the same model as the n8n and LangGraph builds. Step 3 connects it.
- **[The repository](https://github.com/GoldenPassport/digital-branch-concierge)**, which holds the two apps, the workflow, the evaluation dataset and the Mentor prompts that built them. It is linked in Setup files below.

Use the supplied demo records, not real customer data. The skills simulate their actions: the contact change creates a request that the decision owner's approval applies to a demo record, and nothing reaches a real banking system. This is a learning build, not a production banking service or a certification of regulatory compliance. Model responses may vary, so compare each run with the expected route rather than expecting identical wording.

<Callout>

**Why not stay on the free trial model?** The Personal Edition's trial Claude Haiku 4.5 needs no key, and every step on this page also works on it. It has a request quota and a rate limit, though, and an evaluation run sends many calls close together, so the evaluation in Observations stalled on it. DeepSeek keeps the model the same as in the other builds and avoids the limit. To stay on the trial model, skip step 3 and choose **TrialClaudeHaiku4_5** as the agent's AI model after importing the agentic app in step 4.

</Callout>

## Build it

The walkthrough has four parts: **Setup** imports the apps and the workflow and makes the Portal changes they need, **Review** reads what was built, **Run it** exercises the test conversations, including a decision by a named person, and **Observations** shows where to find the evidence behind the scorecard.

### Setup

<ProcessSteps>

<ProcessStep title="Install ODC Studio and sign in" outcome="ODC Studio signed in to your Personal Edition, showing your assets.">

You need a free ODC Personal Edition. The two apps open in ODC Studio, the desktop editor; everything else happens in the Portal in your browser.

- In ODC Portal, open **Apps** and select **Download ODC Studio**. Install it and open it.
- On **Log in to OutSystems Developer Cloud**, enter your organisation address in **Organization**: the host part of your Portal address, such as `yourname.outsystems.dev`, without `https://` or a path. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-studio-login.webp" alt="The ODC Studio sign-in window: Log in to OutSystems Developer Cloud, an Organization field with the placeholder organizationsubdomain.outsystems.dev, a hint to copy the URL from the Portal and a Continue in browser button." caption="Signing in to ODC Studio" />
- Select **Continue in browser**, sign in and allow the browser to open ODC Studio. The session expires after a while; when it does, Studio asks you to sign in again the same way.

</ProcessStep>

<ProcessStep title="Turn on the prompt attack guardrail" outcome="prompt attack detection active for every agent in the Development stage.">

Guardrails are a Portal setting, not code, so they are not in the app files.

- In the Portal, open **Configure > Agent guardrails** and select **Edit**. Switch on **Prompt attack detection** and keep **Block request and raise exception**. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-guardrail.webp" alt="Agent guardrails in ODC Portal for the Development stage: Prompt attack detection is Active, with On detection set to Block request and raise exception rather than Log and continue." caption="Prompt attack detection, set to block" />
- Select **Save**, then confirm **Save and apply agent guardrails**. The setting applies to every agent in the stage and takes a minute or so to come into effect.

</ProcessStep>

<ProcessStep title="Add DeepSeek as an AI model" outcome="a deepseek-flash AI model in the Portal whose endpoint test passed, ready for the agentic app.">

Models are managed in the Portal and shared by every app in the organisation. The agentic app expects a model named `deepseek-flash`. DeepSeek's API follows the OpenAI chat completions format, so it connects as a custom connection.

- Create an API key at **platform.deepseek.com > API keys** and copy it straight away; it is shown only once.
- In the Portal, open **Integrate > AI models**, select **Add AI model**, choose **Custom connection** on the Provider tab and name the model <CopyRequest text="deepseek-flash">`deepseek-flash`</CopyRequest>.
- Under **Endpoints**, select **Add** and fill in the endpoint: **Name** and **Model ID** <CopyRequest text="deepseek-flash">`deepseek-flash`</CopyRequest>, **URL** <CopyRequest text="https://api.deepseek.com">`https://api.deepseek.com`</CopyRequest> (ODC adds `/chat/completions` itself, shown beside the field) and **Priority** 1. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-deepseek-endpoint.webp" alt="The Add endpoint dialog for a custom connection: Name deepseek-flash, Model ID deepseek-flash, URL https://api.deepseek.com with /chat/completions shown after the field, and Priority 1." caption="The DeepSeek endpoint" />
- Under **Headers**, add <CopyRequest text="Authorization">`Authorization`</CopyRequest> with the value `Bearer ` followed by your key (the word Bearer, one space, then the key), for example `Bearer sk-XXXXXX`, and <CopyRequest text="Content-Type">`Content-Type`</CopyRequest> with the value <CopyRequest text="application/json">`application/json`</CopyRequest>. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-deepseek-headers.webp" alt="The Headers section with two key-value pairs, Authorization and Content-Type, values masked." caption="The two headers, values masked" />
- Select **Test endpoint**, then **Add**. **Add** only keeps the endpoint in the form: select **Save** on the model page as well, or the model never appears in Studio.

<Guide label="If the endpoint test fails" title="If the DeepSeek endpoint test fails">

- **401 "auth header format should be Bearer sk-..."**: the header value is missing `Bearer ` or the key is wrong.
- **500 "Connection error" or 404**: the URL has a typo or already includes `/chat/completions`.
- **400 "api key ... is invalid"** with the OpenAI provider: use **Custom connection** instead, with the headers above.

</Guide>

A custom connection can hold several endpoints with priorities, so a second provider can take over when the first fails, and a daily token limit caps what the model can spend. Both are governance settings in the Portal rather than code in the app.

</ProcessStep>

<ProcessStep title="Import and publish the two apps" outcome="Branch Concierge Demo and its test app published in your Development stage, with the agent on deepseek-flash.">

The agentic app comes first, because the test app uses its public actions, events and role.

- In ODC Studio, choose **Organization > Open Files** and open `Branch Concierge Demo.oml` from `outsystems/oml`. {/* TODO screenshot: Open Files and the imported app in Studio. */}
- Open the agent, in **Automations > Agents > CallAgent**, and check **AI model** is `deepseek_flash`. If you named the model differently in step 3, or stayed on the trial model, choose it here.
- Select **1-Click Publish**. Publishing also seeds the four demo customers, the skill registry and the knowledge sections. When it finishes, the panel shows **Test agent in an app**.
- Open `Branch Concierge Demo test app.oml` the same way. If Studio reports outdated references, open **Manage dependencies**, refresh Branch Concierge Demo and select **Apply**. Then select **1-Click Publish**.
- Studio may say the server holds a newer revision when you publish over an earlier import. Select **Compare** to see the differences before choosing **Merge and publish**.

</ProcessStep>

<ProcessStep title="Import and publish the workflow" outcome="the ConciergeRequest workflow published and listening for customer requests.">

The workflow is the process around the agent. It is imported in the Portal, not in Studio.

- In the Portal, open **Workflows**, select **Import** and choose `ConciergeRequest.oml` from `outsystems/workflow`. Import opens the workflow editor in a new tab with an **Import workflow** dialog. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-import-workflow.webp" alt="The Import workflow dialog in the ODC workflow editor: a Browse button, or drag and drop a file, with Cancel and Import buttons." caption="Importing the workflow file" />
- Open it and select **Publish**. It starts on the `CustomerRequestReceived` event from Branch Concierge Demo, so publish the apps first.
- The workflow editor allows one open tab per workflow. If it says the workflow is already open, close the other tab.

</ProcessStep>

<ProcessStep title="Make yourself the decision owner" outcome="your user holds the DecisionOwner role and can sign in to the Review cases screen.">

Review cases are assigned to a role, not to a named account in the app, so the person who answers for a decision is set in the Portal.

- In the Portal, open **Govern > Users**, select your user, then the **End-user access** tab and **Manage roles**. Choose Branch Concierge Demo, the **Development** stage and the **DecisionOwner** role, and save. The role then appears on the tab. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-decision-owner-role.webp" alt="A user's End-user access tab in ODC Portal: End-user roles for the Development stage, with a Manage roles button and one row: asset Branch Concierge Demo, role DecisionOwner, stage Development, directly assigned." caption="The DecisionOwner role, assigned to your user for the Development stage" />
- The test app's Review cases screen signs staff in through the stage's identity provider, the same account you use for the Portal. In the Personal Edition that provider is **OutSystems Community**. If yours is different, open **Govern > Identity providers** to see its name and change it in the test app's `DoExternalLogin` action. <Shot src="/posts/digital-branch-concierge/outsystems-steps/setup-identity-providers.webp" alt="Identity providers in ODC Portal: the Built-in provider, OutSystems Developer Cloud, used by one stage, and OutSystems Community, OpenID Connect with no group mappings, used by the organisation and one stage." caption="The two identity providers in a Personal Edition; staff sign in through OutSystems Community" />

</ProcessStep>

</ProcessSteps>

### Review

<ProcessSteps start={7}>

<ProcessStep title="Read the agent before you run it" outcome="you can point at the seven actions the agent may call, the loop limit and the session the process binds.">

- In ODC Studio, open the agentic app and **Automations > Agents > CallAgent**. **Action calling** lists the seven actions it may call: four skills and three read-only tools. <Shot src="/posts/digital-branch-concierge/outsystems-steps/build-agent-actions.webp" alt="The agent editor in ODC Studio: the AI model, the Action calling tab listing book_appointment, fetch_balance, find_slots, knowledge and opening_hours, and on the right the Logic tree with Authorise, the skills, ImpactPolicyGate and the agent's seven actions." caption="The agent and its actions" />
- Under **Action calling settings**, the **Call Condition** reads `TotalCallsCount >= 6`. When it becomes true, the agent stops calling actions. Mentor first set it to `True`, which would have stopped the agent calling any skill at all; OutSystems' documentation describes `TotalCallsCount`, `LoopCount` and `TokenUsage` for exactly this limit. <Shot src="/posts/digital-branch-concierge/outsystems-steps/build-call-condition.webp" alt="Action calling settings with the Call Condition set to TotalCallsCount >= 6." caption="The loop limit" />
- Expand an action to see where each input comes from. The model fills in the field and the value; the session, and so the customer, is bound by the process. <Shot src="/posts/digital-branch-concierge/outsystems-steps/build-session-bound.webp" alt="The update_contact_details action expanded in the agent editor: Field and NewValue are Generated by AI, each with a description, while SessionId is bound to the flow's SessionId, described as the session identifier used to look up the identified customer." caption="The model chooses the value, never the customer" />

</ProcessStep>

<ProcessStep title="Read a skill" outcome="you can point at the check that stops a risky action before it happens.">

- Open **Logic > Server Actions > UpdateContactDetails**. Its first step calls Authorise, which looks up the session's customer and the skill's risk in the Capability registry and writes a DecisionLog row whatever the answer. A refused call never reaches the work.
- Follow the flow: the skill creates a ContactChangeRequest with status pending. It never edits the customer record; only the decision owner's approval applies the change. <Shot src="/posts/digital-branch-concierge/outsystems-steps/review-skill-update-contact.webp" alt="The UpdateContactDetails server action in ODC Studio, top to bottom: Start, CallAuthorise, a decision on CallAuthorise.IsAuthorised whose False branch goes to a JsonResult refusal, IsValid and a decision whose False branch goes to another JsonResult, then GetSession, Assign, CreateContactChangeRequest, JsonResult, Result and End." caption="The skill: Authorise first, a refusal never reaches the work, and the work is only a pending request" />

</ProcessStep>

<ProcessStep title="Follow the outer process" outcome="you can trace where the agent, the gate, the person and the reply each sit, and what happens when nobody decides in time.">

The workflow is the article's process orchestration layer. It holds no business rules: it runs the standard steps in order and follows the gate's flag.

- In the Portal, open **Workflows > ConciergeRequest**. Read it top to bottom. <Shot src="/posts/digital-branch-concierge/outsystems-steps/review-workflow.webp" alt="The ConciergeRequest workflow in the ODC workflow editor: Start on CustomerRequestReceived, RunAgent, RunImpactPolicyGate and a GateFlag decision. StraightThrough goes to DeliverAgentReply and End. NeedsReview goes to DeliverHoldingReply, then DecideReviewCase, assigned to the DecisionOwner role, closing on ReviewDecided with a one-day timeout, then a DecidedInTime decision: Decided goes to RunAgentFollowUp, DeliverOutcome and End; TimedOut goes to DeliverStaffWillContact and End." caption="The process around the agent: the agent, the gate, a named role and a deadline" />
- **Start** listens for `CustomerRequestReceived`, raised when the customer sends a message. Each request starts one instance, labelled with the customer, the session and the start of the message, so a chat turn, an instance, an agent run and a review case can be traced to each other.
- **RunAgent** runs the agent; **RunImpactPolicyGate** runs the gate as its own step and, when it holds the reply, creates the review case.
- **GateFlag** follows the gate. Straight through delivers the agent's reply. A held reply sends the customer a holding message, then waits at **DecideReviewCase**, a human activity assigned to the DecisionOwner role. It closes only when that case's decision is recorded.
- **DecidedInTime** checks the human activity's `HasExpired` property, the pattern ODC recommends for SLAs. A decision goes to **RunAgentFollowUp**, where the agent words the outcome for the customer but cannot change it; the gate checks that wording too. No decision in time sends "A member of staff will contact you about this shortly" instead.
- A step that fails puts the instance into the Error status, visible in the Portal, instead of failing silently.

</ProcessStep>

<ProcessStep title="Check the gate fails safe" outcome="only an explicit, positive result reaches the customer directly.">

- In the agentic app, open **Logic > Server Actions > ImpactPolicyGate**. It makes no model call. It adds a reason for medium or high skill risk, an unidentified customer, an open complaint, a vulnerability flag, a policy keyword now or earlier in the conversation, an empty reply or a reply that claims an outcome the concierge must never decide.
- The route is straight through only when there are no reasons. Anything else, including a reason nobody planned for, goes to a person.
- Open `CallBranchConcierge`, the service action the evaluations call, to see the gate in its process. The turn's audit rows give the highest skill risk (MaxRisk), the gate decides (CallImpactPolicyGate), and a held reply becomes a review case. `RunImpactPolicyGate`, the workflow's step, does the same with the same logic. <Shot src="/posts/digital-branch-concierge/outsystems-steps/review-gate-highlighted.webp" alt="The CallBranchConcierge service action in ODC Studio. Centre: Start, TurnStart, AgentFlow, GetTurnDecisionLog, a loop over GetTurnDecisionLog.List with an Assign, MaxRisk, CallImpactPolicyGate and a decision on the gate's Route: true goes to GetSessionForReview, Assign, CreateReviewCase, ReviewResponse and End; false goes to Response and End. Left: AllExceptions, ExceptionMsg and a check for Guardrail in the message: false re-raises GuardrailException; true checks for policy keywords such as loan, optionally updates the session's policy flag, then Assign, CreateGuardrailDecisionLog, GuardrailResponse and End." caption="The gate, highlighted: after the agent and before the reply, with the guardrail handler on the left" />

</ProcessStep>

</ProcessSteps>

### Run it

<ProcessSteps start={11}>

<ProcessStep title="Ask a routine question" badge="Straight through" outcome="a reply delivered by the workflow, answered from the bank's own documents.">

- Open the test app from Studio (**Open in browser**) or from the Portal's **Apps**. Enter <CopyRequest text="C1003">`C1003`</CopyRequest> as the **CustomerId** on the left, then ask <CopyRequest text="What time do you close on Saturday?">"What time do you close on Saturday?"</CopyRequest>. <Shot src="/posts/digital-branch-concierge/outsystems-steps/run-t02-workflow.webp" alt="The test app chat for customer C1003: the customer asks What time do you close on Saturday? and the agent replies We're open 09:00 to 13:00 on Saturdays, and we're closed on bank holidays, then asks if there is anything else, with Route straight_through and no reasons under the reply." caption="T02 answered through the workflow, straight through" />
- The reply arrives a little later, between 20 and 40 seconds on this run, because the workflow starts the instance asynchronously: the chat raised the request, the workflow ran the agent and the gate and delivered the reply. The Route under it reads straight_through.

</ProcessStep>

The `OpeningHours` action Mentor wrote searched for "sat" from position 1, so it never matched "saturday" and every weekend day fell through to weekday hours. The manual T02 run in step 11 passed only because, that time, the model answered from the knowledge documents instead of calling the action. Changing the start position to 0 fixed it.

The audit log showed why: in ODC Studio, open the **Data** tab and double-click the DecisionLog entity to see its rows. Every turn with no authorise row had been rated high. Mentor had written the gate's risk as `If(GetTurnDecisionLog.Count > 0, "low", "high")`, so no skill meant high risk. OutSystems put the article's outer process somewhere a business reader can see it. The workflow shows the agent, the gate, a named role and a deadline, and the person who answers for a decision is set in the Portal and signs in with their own account. The Portal also brought the evidence: traces of every run, guardrails as a setting, and an evaluation suite with model judges that found real bugs.

The build was also a test of AI-assisted development. Mentor built most of the two apps from plain-language prompts in hours, not days. Its work needed the same review as anyone else's, and the evaluation and the audit log were what caught the bugs it introduced.

Three opportunities could make that foundation stronger for enterprise teams:

1. **Approval and review as separate paths.** The gate has one review route. Splitting actions that need approval from replies that need review, with send-back to the agent, would match the decision to the risk.
2. **SLAs in working hours.** The human activity's timeout is calendar time. Deadlines in business hours, with escalation, would make the decision owner's commitment measurable.
3. **A reviewed learning loop.** Each human decision could become a lesson that a person promotes, and a test case that guards it.

These are opportunities to build on a positive result, not reasons to hold back.

### Potential findings

These are early observations from a limited number of runs on an ODC Personal Edition. I may have missed a setting or misread a result, so treat them as things to check in your own setup rather than settled conclusions.

<ScrollCards label="Seven potential findings from initial testing" hint="Scroll through the seven findings">

<ScrollCard number="01" title="Mentor's work needs review like anyone's">

Mentor set the agent's call condition to `True`, which stops it calling any skill, and wrote two logic bugs that the evaluation found. It also reported published elements as unpublished, and built a login form against the wrong identity provider with a plain-text password field. Each was caught by checking its change against the documentation and the run logs.

</ScrollCard>

<ScrollCard number="02" title="Workflow decisions take basic types">

A workflow decision could not read a structure returned by an action, only basic types, so a check on a review case's status could not be written that way. The human activity's own `HasExpired` property was enough for the deadline, and actions that return simple values avoid the problem.

</ScrollCard>

<ScrollCard number="03" title="No working-hours calendar for SLAs">

A human activity's timeout is a duration or an expression. I did not find a business calendar, so a deadline in working hours has to be calculated in the app and passed to the timeout.

</ScrollCard>

<ScrollCard number="04" title="An app cannot raise another app's event">

The chat could not raise the agentic app's `CustomerRequestReceived` event directly, only handle it. A one-line public action in the agentic app that raises the event solved it.

</ScrollCard>

<ScrollCard number="05" title="The guardrail exception is not named in the documentation">

Prompt attack detection blocks the request and raises an exception, but I did not find the exception's name in the documentation, so the handler matches on the message text. A refused request also never reaches the gate, so it is not remembered as an earlier policy request in the conversation.

</ScrollCard>

<ScrollCard number="06" title="Fixed session ids make runs depend on each other">

The agent's memory is stored per session, and the dataset gave each case a fixed session id, so each evaluation run continued the previous run's conversations. New session ids, or a setup action that clears memory, keep runs independent.

</ScrollCard>

<ScrollCard number="07" title="A daily trace limit can blind the evaluation">

The Personal Edition's Development stage has a daily trace limit, and the asynchronous chat, polling for replies every two seconds, used it up by early afternoon. After that the Tool Trajectory judge saw no tool calls and failed every case that expected one, although the agent had called them. A slower poll, or a push from the workflow, would spend far fewer traces. <Shot src="/posts/digital-branch-concierge/outsystems-steps/obs-trace-limit.webp" alt="ODC Portal Traces with a warning: Your organization reached the daily trace limit in Development stage at 02:03 PM on Oct 16, so traces and analytics data will be incomplete until 01:00 AM, Oct 17. Can a low-code platform give an agent room to act while keeping consequential decisions with people? This build offers a promising answer. Routine requests went straight through, higher-impact requests waited for a named person, and that person's decision, not the agent's, decided what happened.

What stayed with me was how much of the governance is a setting rather than code: who may decide, which model runs, what the guardrails block and which judges score each change. That suits an organisation where the people accountable for those choices are not the people writing the app.

My score of **8 out of 10** reflects that foundation, not a claim of production readiness. The opportunities above set out what would take it further.
